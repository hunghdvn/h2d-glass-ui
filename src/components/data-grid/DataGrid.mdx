# DataGrid

Rows of data in typed columns, drawn in the look of a [Table](?path=/docs/components-table--docs).
The grid is the part of the library that knows about the data. It reads the columns, formats each
value for its type and its locale, draws the rows with a sticky heading, sorts them, pages them,
chooses rows, groups them with totals, opens a detail under a row, moves rows, adds, edits and
deletes rows (in the row, in a cell, in a batch, in a form or in a popup), draws a long list by
windows, filters them (a search field that marks what it finds, a row of filter cells, a funnel on
each title that lists the values, and a bar that says the conditions), exports them as CSV, says when
it loads and when it is empty, and has a keyboard.

Use it for a screen of records that people sort, search, filter and change: orders, customers, a
queue of tickets. For a short list of rows you write yourself, a `Table` is lighter. The grid is one
component with one set of props, and this page lists all of them. For the grid in a whole screen, see
[Examples/Data grid](?path=/docs/examples-data-grid--docs).

```tsx
import { DataGrid } from 'h2d-glass-ui';
import type { DataGridColumn } from 'h2d-glass-ui';

interface Order {
  id: string;
  customer: string;
  date: string; // '2026-11-05'
  total: number;
}

const columns: DataGridColumn<Order>[] = [
  { field: 'id', caption: 'Order', rowHeader: true, width: 104 },
  { field: 'customer', caption: 'Customer' },
  { field: 'date', caption: 'Order date', dataType: 'date', width: 140 },
  {
    field: 'total',
    caption: 'Total',
    dataType: 'number',
    format: { style: 'currency', currency: 'VND' },
  },
];

<DataGrid data={orders} rowKey="id" columns={columns} caption="Orders" locale="vi-VN" />;
```

## Table or DataGrid

Use a `Table` when you write the cells yourself and the data is small, or when the table is mostly
text. Use a `DataGrid` when the data is an array of rows and the table should be made from it: the
columns say what each value is, and the grid shows it. The two look the same, because the grid draws
its rows with the classes of a Table: the variants, the sizes, the hover and the chosen row are the
Table's own.

## Rows and keys

`data` is the rows; the grid reads them and never changes them, so a changed row is a new object. An
edit of one row that makes a new array with a new object for that row (`data.map(…)`) draws that row
again and no other: a row that is the same object, with the same key, at the same place, is kept as
it was. `rowKey` says what a row is known by: the name of a property of the row, or a function of
the row. The key is a string or a finite number, and each row needs its own. A row with no usable
key is known by its place in the list, and two rows with the same key are both drawn, as separate
rows that selection treats as one; the keyboard goes on from either. Both cases warn once in
development, and so does the place of a row with no key that is the key of another row. Keys are
checked when `data`, `rowKey` or the order of the rows changes, and not at all in production.

A `rowKey` function is the one of each render: new data and a new function given together are read
with each other at once. A function written in the JSX is a new one on every render, so on every
render the grid reads every row's key with it again; when the keys are the same nothing else is
done, and no row is drawn again. A property name, or a function made once (outside the component, or
in `useCallback`), costs not even that. Give it a function of the row alone.

## Columns

`columns` is an array of objects, not a list of child elements, so that `field` and the functions
of a column keep the type of the row. A column reads a property of the row (`field`), or computes
its value (`id` and `value`):

```tsx
const columns: DataGridColumn<Order>[] = [
  { field: 'total', dataType: 'number' },
  { id: 'tax', caption: 'Tax', dataType: 'number', value: (order) => order.total / 5 },
];
```

`field` takes only the names of properties of the row, as strings, and the `cell` and `format` of
that column take `value` of that property's type. This is why the column is a union: a column with
a `field` and a column with a `value` are different shapes, and the type of the field's column is
made for each property. The union is by design, so a type error on a column can be long; read the
last lines of it.

A column that computes its value has no field to name it, so it needs an `id`. An `id` is also what
the state of the grid will call a column. It is the field when there is no `id`.

The type of a computed column is lost when you write it inline in an array of `DataGridColumn`.
`dataGridColumn` keeps it:

```tsx
import { dataGridColumn } from 'h2d-glass-ui';

const tax = dataGridColumn<Order>()({
  id: 'tax',
  caption: 'Tax',
  value: (order) => order.total / 5, // V is number
  cell: ({ value }) => value.toFixed(0), // value: number
});
```

| Column field           | Does                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------ |
| `caption`              | The title of the column; the id when left out                                                          |
| `dataType`             | `'string'` (default), `'number'`, `'date'`, `'datetime'` or `'boolean'`; see below                     |
| `format`               | Intl options for the type, or a function `(value, row) => string`                                      |
| `cell`                 | A function of `{ row, rowKey, value, text, column, selected, highlight }` that returns the content     |
| `align`                | `'start'`, `'center'` or `'end'`; by the type when left out                                            |
| `width`                | A width in pixels. Without it the column is flexible                                                   |
| `minWidth`             | The least width of a flexible column in pixels; 60 when left out                                       |
| `pinned`               | `'left'` or `'right'`: the zone the column starts in; see Column layout                                |
| `visible`              | `false` starts the column hidden; see Column layout                                                    |
| `rowHeader`            | Draws the column as the heading of its row (`th scope="row"`); the first one wins                      |
| `lookup`               | `{ items, valueField, displayField, searchable }`: the value is a key, and the text is the item's      |
| `allowSorting`         | Whether the title is a button that sorts; the grid's `allowSorting` when left out                      |
| `allowResizing`        | Whether the column has a handle that resizes it; the grid's `allowResizing` when left out              |
| `allowReordering`      | Whether the column can be moved by a drag or the keys; the grid's `allowReordering` when left out      |
| `allowPinning`         | Whether its menu can pin and unpin the column; the grid's `allowPinning` when left out                 |
| `allowHiding`          | Whether its menu can hide the column; the grid's `allowHiding` when left out                           |
| `sortValue`            | A function `(row) => value` that the column is sorted by, in place of its value                        |
| `exportable`           | Whether the column is in the CSV; `true` when left out; see CSV export                                 |
| `allowSearch`          | Whether the search reads the column and its cells are marked; `true` when left out                     |
| `allowFiltering`       | Whether the column has a cell in the filter row; the grid's `allowFiltering` when left out             |
| `filterOperators`      | The operators of its filter cell, narrowed from its type, in the type's order                          |
| `allowHeaderFiltering` | Whether the column has a funnel; the grid's `allowHeaderFiltering` when left out                       |
| `headerFilter`         | `{ values }`: the values the funnel lists in server mode, each with its `value` and `text`             |
| `allowEditing`         | Whether the cell can be edited, or a function of the row; `true` when left out; see Editing            |
| `setValue`             | Of a computed column: `(row, value) => fields` that turns an edited value into fields of the row       |
| `validationRules`      | A list of rules the value must pass when it is edited; see Validation                                  |
| `editor`               | A function of the editor's context that returns the editor, in place of the one of its type            |
| `multiline`            | A string column of long text, which the cell modes show as text; the form and the popup edit it        |
| `form`                 | `{ visible, span }`: `visible: false` leaves it out of the form and the popup; `span: 2` makes it full |

A column with no usable `field`, or with an `id` that an earlier column has, or with an `id` that
starts with `flg:` (the grid's own columns will use it), is left out with a warning. A field that no
row of the first twenty has warns once, which is how a misspelt field shows.

### The type of a column

| `dataType`   | Aligned to | Shown as                                                                  |
| ------------ | ---------- | ------------------------------------------------------------------------- |
| `'string'`   | the start  | The text, which is cut with an ellipsis when it is longer than its column |
| `'number'`   | the end    | `Intl.NumberFormat` for the locale; `format` gives its options            |
| `'date'`     | the start  | The calendar day, `11/05/2026` in `en-US` and `05/11/2026` in `vi-VN`     |
| `'datetime'` | the start  | The date and the time, short, in `timeZone`                               |
| `'boolean'`  | the centre | A check for `true`, nothing for `false`; both have their words, hidden    |

A value the type does not accept (a string in a number column) is shown as nothing, and a warning
says so once, without the value. A blank (`null`, `undefined`, `''`, `NaN`, an invalid date) is
shown as nothing too: the cell is empty.

A boolean's check is drawn for `true` and the cell holds the hidden word `labels.yes`; `false` draws
nothing and holds `labels.no`. The words are the text of the cell, which is what a screen reader
reads. A boolean column with words of your own, a `format` function or a `lookup`, draws them as a
cell of text does, in the column's alignment, and no check: `(paid) => (paid ? 'Paid' : 'Owed')`
shows both words. Intl options mean nothing for a boolean, and leave the check.

### Dates and `timeZone`

A `date` is a calendar day with no hour, as in `DatePicker`: a `Date`, which is read in UTC, or a
`YYYY-MM-DD` string, and nothing else. It is shown as that day whatever the zone of the machine, so
the server and the browser write the same text. Its `format` cannot move it to another zone: a
`timeZone` in the options is not used, since a calendar day has no zone (it is written in UTC).

A `datetime` is an instant: a `Date`, a number of milliseconds, or an ISO 8601 string **with an
offset** (`2026-11-05T09:30:00+07:00` or `…Z`). A string with no offset is shown as nothing and
warns, since JavaScript would read it in the zone of the machine, which is not the same on the
server and in the browser. It is shown in the grid's `timeZone`, `'UTC'` when left out, for the same
reason. Pass the zone of the person (from a cookie or a profile) to show their hours; an invalid
zone is `'UTC'` with a warning. A `timeZone` in the column's own `format` options wins over the
grid's for that column, and the day the filters read is the day in that zone: what the cell shows.

### `cell` and `format`

`format` changes the text of a value; `cell` changes what is drawn. Use `format` when the content is
still text (a search compares that text; a sort compares the value, or `sortValue`), and `cell` for
a Badge, an Avatar or a link. `cell` is called with the row, its key, the raw `value`, the formatted
`text` and an object that describes the `column`; `selected` is `false` until rows can be chosen. A
blank value is not given to `format`: it is shown as nothing.

```tsx
{
  field: 'status',
  caption: 'Status',
  cell: ({ value }) => <Badge variant={value === 'Delivered' ? 'success' : 'warning'}>{value}</Badge>,
}
```

A `cell` is called as a function while its cell renders, and is not a component of its own: to use
a hook, return the element of a component that does.

### Lookup

A column with a `lookup` holds a key and shows the text of the item the key points at:

```tsx
{
  field: 'status',
  caption: 'Status',
  lookup: { items: statuses, valueField: 'id', displayField: 'name' },
}
```

A value that no item has is shown as nothing, with no warning: an app may keep rows that point at an
item that was removed. A `format` function wins over a lookup, and Intl options are ignored for one.
A lookup column is aligned to the start.

### A stable `columns`, `rowClassName`, `labels` and `summary`

The grid prepares the columns when the array changes. A new array on every render, which is what an
array written in the JSX is, prepares them every time and throws away what was remembered of each
cell. After three renders in a row with a new array and the same columns, the grid warns. Write
`columns` as a constant outside the component, or in `useMemo`.

Every row reads `rowClassName` and `labels`, so a new one draws every row again, where a choice
draws only the rows it changes. Write `rowClassName` and the functions of `labels` outside the
component, or in `useCallback` or `useMemo`; after three renders in a row with new ones, the grid
warns. The `labels` object itself may be written in the JSX: the grid keeps the last one while each
value is the same, so labels of words alone cost nothing.

`renderDetail` and `rowHasDetail` are read by every row too (see Master-detail), so a new function
on every render draws every row again, and the grid warns after three renders in a row with a new one:
write them outside the component or in `useCallback`.

`summary` is kept the same way, by value: an object written in the JSX with the same items costs
nothing, and a `type` or a `format` that is a function counts by identity. A `summary` whose
functions are new on every render computes every total again; after three renders in a row the grid
warns, so write the functions in a constant outside the component or in `useMemo`.

## In a Server Component

A column holds functions (`cell`, `format`, `value`), and a function cannot be passed from a Server
Component to a client one. Write the columns and render the grid in a small client component, and
give it only the data, which is plain, from the page:

```tsx
'use client';

import { DataGrid } from 'h2d-glass-ui';

const columns = [/* … */];

export function OrdersGrid({ orders }: { orders: Order[] }) {
  return <DataGrid data={orders} rowKey="id" columns={columns} caption="Orders" />;
}
```

The grid still renders its rows on the server, so the page has them before any script runs.

## Row height: `density` and `variant`

A row has a fixed height, so that a long list can be laid out by arithmetic, and what is in a cell
must fit it: a cell whose content is taller is not cut, it makes its row taller (the height of a
table row is the least it has), and in a virtual grid that row puts every row after it out of the
arithmetic, so the window drifts. Cells have no padding above or below, and centre their content.
The height is set by the `density` and the `variant`:

| `density`       | `lined` | `striped` | `minimal` |
| --------------- | ------- | --------- | --------- |
| `'compact'`     | 31      | 30        | 36        |
| `'standard'`    | 41      | 40        | 52        |
| `'comfortable'` | 49      | 48        | 60        |

The numbers are pixels, for a row whose tallest content is an Avatar `sm` (24px). A `striped` grid
has 2px between its rows, so its rows are that much further apart. `compact` uses the `sm` size of a
Table, with its smaller text. `rowHeight` replaces the number of the table with one of your own: a
finite number above 0, or it warns and the table's number is used. The grid writes the height as
`--flg-data-grid-row-height` on its root, and a grid in a cell of another has its own.

`striped` marks every second row of what is shown, from the first, and not every second child of the
body: the stripes belong to the rows, which matters when a window of rows is drawn (see Virtual
scrolling).

## Height and the sticky heading

With a `height`, a number of pixels or any CSS length (`'60vh'`), the whole grid has that height:
the caption above it, and the frame under the caption, which takes the rest and scrolls. The column
headings stay at the top of the frame while the rows go under them, over a solid colour
(`--flg-data-grid-pin-bg`) so that the text passing under them is not seen through. The grid
measures its heading and gives each row and cell that much scroll margin at the top, so that what
the browser scrolls into view is not left under it. The frame has no scroll padding at the top, as
a Table's has: the headings stick in it, and Chromium and WebKit would scroll the rows for a focus
on a title.

Without a `height` the grid is as tall as its rows, and the heading has nothing to stick to
vertically. The heading is measured only with a `height`, and, for the layer of a load, only while
that layer is there. Its rows have no scroll margin either: the page brings a row to its top.

## Widths

A column with a `width` is that wide. Columns without one are flexible: they share the room that is
left in the frame equally, and none is narrower than its `minWidth`. When the columns need more room
than the frame has, the frame scrolls sideways. When no column is flexible, every column keeps its
width and an empty filler column at the end (before the right zone, when a column is pinned to the
right), hidden from assistive technology and out of reach of the keys, takes the rest of a wider
frame, so the rows, their rules and the heading reach its edge.
It is drawn only when that rest can carry the end of a row: at least 1px, and at least the round
corner of a `striped` row; with less, the table is as wide as its columns.

A classic vertical scrollbar, the kind that takes room from the frame, narrows it. A grid whose
columns all have a width and fill the frame exactly then scrolls sideways by the width of the
scrollbar, which is right, since the columns do not fit. Leave a little room, or make one column
flexible.

The frame is measured after the first render: for the flexible columns, for the filler column, and
for the words of an empty grid (see Loading and empty), which are as wide as the frame. Until then,
and on the server, the stylesheet shares the room out and the filler column is drawn, so the
columns are already in place at the first paint.

reader still reads all of it. There is no tooltip for a cut text.

## Column layout

The layout of the columns is four parts, each keyed by column id: `order`, `widths` (pixels),
`hidden` and `pinned` (`'left'` or `'right'`). It is state like the sort: `columnLayout`,
`defaultColumnLayout` and `onColumnLayoutChange` are a controlled or an uncontrolled value, it is
part of the state `onStateChange` sends (`changed` is `'columnLayout'`) and of `getState()`, and it
holds only what JSON can carry, so it can go to `localStorage` and come back as
`defaultColumnLayout`.

```tsx
<DataGrid
  data={orders}
  rowKey="id"
  columns={columns}
  defaultColumnLayout={saved?.columnLayout}
  onStateChange={(state, changed) => {
    if (changed === 'columnLayout') save(state.columnLayout);
  }}
/>
```

**Where a layout starts.** The order of the `columns` array, the columns that say `visible: false`
hidden, their `pinned` and their `width`. `defaultColumnLayout` gives any of the four parts, and a
part it gives replaces that part whole; the others stay as the columns say. After that the layout is
the grid's: it is never started again, and a later change of a column's `visible`, `pinned` or place
in the array does nothing to a column the layout already holds. In development the grid warns once
when such a change is ignored; change `columnLayout`, or remount the grid with a `key`, instead.

**Known and new columns.** A column whose id is in `order` is laid out by the layout alone: its own
`visible` and `pinned` no longer count, and its own `width` counts only while `widths` has no entry
for it. A column that is not in `order` is new (you added it after the layout was saved, or its
config came after the first render): it goes to the end of its zone, and what the layout's
`hidden`, `pinned` and `widths` say of its id counts, its own values filling in what they do not
say. So a `defaultColumnLayout` counts for columns that arrive later too.

A width from the layout is held to `minWidth` and 2000 pixels in whole pixels, as a resize holds it
(a `minWidth` over 2000 wins), with one exception: the own `width` of a column is always allowed,
even under its `minWidth`. A drag or a key never moves such a width further out: towards the limits
it goes to them. A fit replaces it with the width it measures.

**Zones.** The shown columns are the left zone, then the middle, then the right zone, each in the
order of `order`. The selection column of `selectionMode="multiple"` is no part of the layout: it is
always first, and it is in the left zone when a data column is (see Pinned columns).

**Hidden columns.** A hidden column is not in the DOM and is no column of the grid for the keyboard
or the sort. At least one column is always shown: a layout that hides every column shows the first
in `order`. A hidden column sorts nothing, but its item stays in `sort` and in `getState()`: show
the column again and its level is back, with its number. The next press on a title builds on the
levels that are shown, so it drops the hidden item. That holds where the grid sorts. With `remote`
it sorts nothing and hands `sort` over as it is, the hidden column's item in it, so your server sorts
by it too: drop the item in `onColumnLayoutChange` if you do not want that.

**What is shown.** `getState().columnLayout`, and the layout that `onColumnLayoutChange` and
`onStateChange` receive, are the layout as it is shown: the new columns appended, the ids of no
column dropped, the widths held, and the columns' own widths included for every column that has one.
A controlled layout you do not take stays as it was, and the callback still hears the request.

**What is cleaned without a word.** A layout may come from the storage of an end user, so these say
nothing: ids of no column (and `flg:` ids), ids that are repeated, pins that are neither `'left'` nor
`'right'`, and widths that are out of range or are not a positive number. What its type forbids does
warn once for the prop, in development: a layout that is not an object, an `order` or `hidden` that
is not an array of strings, `widths` or `pinned` that are not objects, a width that is not a number.
The grid uses what it can: an empty part of a controlled layout, no part of a default one.

The keyboard follows a column that moves: the active cell stays on its column. When its column is
hidden or removed, the active cell goes to the column now at the same place, as it does for a row.

A layout written in the JSX (`columnLayout={{ … }}`) is kept while it says the same, so it draws no
row again, and a change of a width draws no row and no title.

## Pinned columns

A column that is pinned to the left or to the right stays at that edge of the frame while the frame
scrolls sideways, and the other columns go under it. `pinned: 'left'` on a column, or a `pinned`
part of `defaultColumnLayout` or of `columnLayout`, says which (see Column layout: the layout decides
where a column starts, and a later change of a column's own `pinned` does nothing). The zones are
the first and the last columns of the grid in the order of the layout, so a pinned column is never
in the middle of the row. The selection column of `selectionMode="multiple"` is pinned to the left
when a data column is, and is not otherwise.

```tsx
<DataGrid
  data={orders}
  rowKey="id"
  columns={columns}
  selectionMode="multiple"
  height={420}
  defaultColumnLayout={{ pinned: { id: 'left', total: 'right' } }}
/>
```

**What sticks, and when it is solid.** A pinned cell, in the heading and in every row, is
transparent while nothing is scrolled under it, like every other cell: a grid at rest looks as it
would without pins, with a line of 1px at the edge of each zone. When the frame has been scrolled
away from an end, the zone at that end turns solid (`--flg-data-grid-pin-bg`), so what scrolls under
it is not seen, and a shadow of 14px (`--flg-data-grid-pin-shadow`) is drawn beside its edge. The
shadow is as tall as the part of the table the frame shows, and never reaches below the last row.
The wash of a stripe, of the pointer and of a chosen row (and the bar of a chosen row of a `lined`
grid) is drawn on a solid cell as on any other. The heading sticks at the top, over the pinned cells
of the rows, as it does over the others. A `striped` or `minimal` frame has 6px of padding, inside
which a sticky cell would stick; the grid takes that back, so no strip of cells that have scrolled
shows beside a zone. In forced colours the pinned cells are `Canvas` and the line at the edge is a
border in the text colour; the shadow and the washes are not drawn.

The grid listens to the scroll of its frame, and measures it, only while a column is pinned, and a
scroll draws nothing of the grid: it writes `data-scrolled-left` and `data-scrolled-right` on the
frame, which the stylesheet reads.

**Keys and scrolling.** The keys go across the zones as across any column, and a key onto a pinned
cell scrolls nothing: the cell is where it is. A cell of the middle that a key, `focus()`, the
handle's `focus()`, `scrollIntoView` or Tab brings into view stops clear of both zones, and not
under them. That is done by a scroll margin, of the width of the zone, on the cells of the middle,
and none on the pinned ones; the frame has no scroll padding at the sides.

**A column without a width, pinned.** A pinned column needs its width to know where the next one
sticks. Until the frame has been measured (on the server, in the first render) a column without a
`width` counts its `minWidth`, a lower bound, so no cell sticks to the right of where it rests in
the HTML of the server; after the frame is measured it counts the pixels it was given.

**The filler column** (see Widths) goes before the right zone, so that the zone ends the row at the
edge of the frame. It is still no column: the keys, Home and End go across it, and a press on it does
nothing.

## Resizing columns

A column that can be resized has a handle on the right edge of its title: a thin line between the
titles that becomes a bar of 3px in the accent under the pointer. `allowResizing` is the default of
every column (`true`), and a column's own `allowResizing` wins; the column of boxes and the column of row handles have none.
The handle is for a pointer: it is hidden from a screen reader and is no stop of Tab, so the keys
below are the way for everyone else.

- **Drag it.** A press that moves 4px or more is a drag, with a mouse, a pen or a finger (the
  handle is 24px wide for a finger, and takes no scroll from it). The column is as wide as the
  pointer says, at least its `minWidth` (60 when left out) and at most 2000px, and it follows the
  frame when it scrolls sideways: a pointer held within 40px of the frame's edge scrolls the frame,
  faster the closer it is, and the column goes on growing. For a column of the middle, the edge is
  that of a pinned zone where there is one, so the 40px are over the columns of the middle. A line
  runs down the grid from the handle, and a label says the width (`labels.columnWidth`). The cursor is `col-resize` over the
  whole page until the pointer is let go. A drag is not a click: the click that its release makes
  is not delivered, so the column is not sorted. <Kbd keys="esc" /> puts the column back as it was.
- **One change, at the release.** While the pointer moves, the widths live in the grid and only
  the table is drawn again: no row, no title and no toolbar. `onColumnLayoutChange` is called once,
  at the release, with the layout as shown (and then `onStateChange(state, 'columnLayout')`); a drag
  that is cancelled, or that ends at the width it began with, calls nothing. A grid that is
  controlled and keeps its `columnLayout` sees the column go back at the release.
- **Columns without a width are frozen.** The first resize of a grid whose columns share the frame
  (the ones with no `width`) writes the width each has at that moment into `columnLayout.widths`,
  with the new width of the column, so a drag makes the table wider or narrower and never takes the
  room of a neighbour. From then on the columns do not follow the width of the window. Only a
  layout with no `widths` for them makes them flexible again; "fit" below sets a width and does not.
  A grid whose columns all have a width has the filler column (see Widths) at the end of its rows
  when the frame is wider than the columns.
- **Fit.** A double press on the handle gives the column the width that its title and the cells it
  has drawn need, at most 600px and at least `minWidth`. It reads the widths from the page and
  changes nothing to do it, so the frame does not scroll. Only the rows that are drawn count: a
  page, or the window of a virtual grid, and not the rows that are not; a column with none fits its
  title. A custom `cell` that stretches to the width of its cell (a block, a flex container) is
  measured at that width, so it does not fit narrower than it is. It is one change of the layout,
  and the clicks of the double press do nothing else.
- **Keys.** <Kbd keys="alt+shift+left" /> and <Kbd keys="alt+shift+right" /> on the title of a
  column make it 10px narrower or wider, within the same limits, and the frozen widths of the others
  come with the first press. Each press is one change of the layout. The new width is said, once,
  half a second after the last press (`labels.announceResized`), and after a fit. The keys are
  cancelled on the title of every data column, also on one that cannot be resized.

```tsx
<DataGrid
  data={orders}
  rowKey="id"
  columns={[
    { field: 'id', caption: 'Order', width: 104, allowResizing: false },
    { field: 'customer', caption: 'Customer', minWidth: 120 },
    { field: 'total', caption: 'Total', dataType: 'number', width: 160 },
  ]}
  columnLayout={layout}
  onColumnLayoutChange={setLayout}
/>
```

The last title of a row has its handle inside the cell, so that it does not widen what the frame
scrolls, and draws no line until the pointer is over it. In forced colours the line is the text
colour and the bar is `Highlight`; with more contrast the line is solid.

## Reordering columns

A column can be moved by dragging its title. `allowReordering` is the default of every column
(`true`), and a column's own `allowReordering` wins; the columns the grid adds itself (the boxes, the row handles, the detail buttons) cannot be moved. A column
that cannot be moved is not a place the others are stopped at: they go past it.

- **Drag the title.** With a mouse or a pen: a finger on a title scrolls the frame, so a touch
  screen moves columns with the keys below and the column menu. The whole title starts the drag,
  its sort button included: a press that stays under 4px is the click of the button, and one that
  goes further is a drag, whose click is not delivered, so a drag never sorts. The handle that
  resizes and the column of boxes do not start one. The column and its cells are dimmed to 35% while
  it is dragged, a chip with the caption follows the pointer (in the top layer, so nothing clips it),
  and a line of 3px with a dot at its top shows where it would go. The cursor is `grabbing` over the
  whole page until the pointer is let go. The frame scrolls sideways when the pointer is within 40px
  of its edge; for a column of the middle, of the inner edge of a pinned zone where there is one, so
  the line still shows where the frame starts to scroll.
- **Within the zone.** A column moves among the columns of its own zone: the pinned ones on the left,
  the ones in the middle, the pinned ones on the right (see Pinned columns). Over another zone, below
  the heading, beside the column itself, or where the boundary is out of sight under a pinned zone,
  there is no line and a drop does nothing. <Kbd keys="esc" /> puts everything back.
- **One change, at the drop.** `onColumnLayoutChange` is called once, at the drop, with the layout
  as shown (and then `onStateChange(state, 'columnLayout')`); a drag that is cancelled, or dropped
  where nothing moves, calls nothing. The rows are drawn when the drag starts, which is when the
  column is dimmed, and when it ends, and not for a move of the pointer. A hidden column keeps its
  place among the others. The new place is said (`labels.announceMoved`): the number of the column
  among the columns that are shown, and how many there are.
- **Keys.** <Kbd keys="mod+shift+left" /> and <Kbd keys="mod+shift+right" /> on the title of a
  column move it one place within its zone, past the next column that is shown. Each press is one
  change of the layout. The title keeps the focus and is scrolled to, sideways, if it moved out of
  sight. The keys are cancelled on the title of every data column, also where nothing changes (the
  edge of the zone, a column that cannot be moved). The touch table above says what a finger does.

## The column menu

Every data column has a menu of what can be done to it, with one menu for the whole grid, drawn after
the table (so that the title a screen reader reads stays short). It is the menu of the library, 236px
wide, and its items are one change each: its callbacks are called once, and what it did is said
through the grid's live region.

- **Where it opens from.** A button with three dots at the end of the title (`aria-haspopup="menu"`,
  `aria-expanded`, `aria-controls` while it is open, named by `labels.columnMenu`): the menu opens
  under it. The button is drawn only while its title is hovered, has the focus or holds it, or while
  its menu is open, and always on a device with no hover; it keeps its room, so a title does not move
  when it shows, and it stays in the accessibility tree. A right press on a title opens the menu at
  the pointer, when the press ends. <Kbd keys="alt+down" />, <Kbd keys="shift+f10" /> and the
  ContextMenu key on a title open it under the button, once for a key that is held; the keys are
  cancelled on the title of every data column, also where the column has no menu. The title of the
  column of boxes, and a column that has no menu, have no button and leave the right press to the
  browser. A second press on the button of the open menu closes it, and the button of another title
  closes it and opens that column's.
- **What is in it.** In groups set apart by a line; a group with nothing in it, and its line, are
  left out, and a column with nothing at all has no button.
  1. `allowSorting`: Sort ascending, Sort descending (each makes the column the only level of the
     sort, in that direction), and Clear sorting (takes this column's level out and keeps the others;
     off when the column is not sorted).
  2. Group by this column, when the grid draws the group panel (a user who groups needs a chip to
     ungroup by), is not in server mode, the column allows grouping and grouping it leaves a data
     column shown: more than one is shown (as hiding needs), or the column stays shown when grouped
     (`showWhenGrouped`). It adds the column as the last level, ascending, and says
     `announceGrouped`. For a column that is grouped by and still shown (`showWhenGrouped`) the item
     is there and off. A column that only groups has a button for its menu in a grid that draws
     the panel.
  3. `allowPinning`: Pin to the left, Pin to the right, and Unpin when the column is pinned. The item
     of the side the column is pinned on is off.
  4. `allowReordering`: Move left and Move right, which are off at the edge of the zone of the column;
     `allowResizing`: Fit width to content (see Resizing columns).
  5. `allowHiding`, and more than one data column shown: Hide column.

  `allowPinning` and `allowHiding` are the defaults of every column of the grid, `true` when left
  out, and a column's own wins. A column that is pinned or hidden by its own fields or by the layout
  stays so whatever they say. A column hidden from its menu is in `hidden` of the layout, and can be
  shown by a layout that leaves it out.

- **What it says.** Sorting is said as a press on a title says it (`announceSort`,
  `announceSortCleared`); `announcePinned`, `announceUnpinned`, `announceHidden` and
  `announceMoved` say the rest.
- **Where the focus goes.** The menu opens on its first item, and the arrows and the first letters
  move among the items. When it closes, by <Kbd keys="esc" />, by an item or by a press elsewhere on
  the grid, the focus goes to the title it was opened for: the title that took the place of a column
  that was hidden, and the pinned title in its new place. The page and the frame are not scrolled.

## Choosing columns

`columnChooser` puts a button at the end of the toolbar (an icon button of the library, named by
`labels.columnChooser`, with a tooltip that does not repeat its name as a description). It opens a
Popover of the library, 220px wide, under the button and lined up with its end: a title, and one
box for each data column, with the caption of the column as its label.

- **The order.** The order the grid shows: the left zone, the middle, then the right zone, and a
  hidden column at its place in the layout's `order`. The column of boxes of `selectionMode` has
  none.
- **A box is a change at once.** There is no OK button. Clearing a box hides its column and checking
  it shows the column again: one change of the layout, one `onColumnLayoutChange` (and
  `onStateChange` with `'columnLayout'`), and one thing said, `announceHidden` or `announceShown`,
  because the grid changes behind the popover, out of sight. The popover stays open for the next
  box, and the focus stays on the box that was pressed. A grid whose parent holds the layout and does
  not change it leaves the box as it was.
- **A column that is always shown.** A column with `allowHiding: false` has its box checked and
  disabled, in a row with a lock at the other end, and the box is described by `labels.lockedColumn`
  (hidden from the eye). A layout can still hide such a column (`visible: false`, or a saved layout):
  its box is then unchecked and can be checked, and once it is shown it is locked again.
- **The last column shown.** Its box is disabled while it is the only one shown, so that the grid is
  never left with no column. It has no lock: the lock is for a column that says it is always shown. Its
  box is described by `labels.lastShownColumn` (hidden from the eye) for as long as it is the only one,
  and a column that is both locked and the last keeps the description of the lock alone.
- **The keys.** The button is a stop of Tab of its own, before the table. <Kbd keys="enter" /> or
  <Kbd keys="space" /> on it opens the popover, with the focus on its first box that can change;
  <Kbd keys="space" /> changes the box that has the focus, <Kbd keys="tab" /> moves among the boxes,
  and <Kbd keys="esc" /> closes the popover and gives the focus back to the button.

Without `columnChooser` no button is drawn and no popover is mounted.

## CSV export

`csvExport` adds a button after the column chooser (an icon button named by `labels.exportCsv`, with
a tooltip that says the same name) that downloads the rows as a CSV file. `true` takes the defaults
and an object takes the options of `DataGridCsvOptions`. The handle's `exportCsv(options)` does the
same without a button: it always returns the text, and it downloads the file when the call says
`download: true` or gives a `fileName` (`download: false` turns that off). The button calls the same
function with `download: true`, so the two ways to export always agree. The options of a call are
laid over those of `csvExport`, and `exportCsv()` works without the prop, which only adds the button.
A `fileName` in `csvExport` names the download of the button; it never starts one by itself.

| Option           | Default       | Is                                                                         |
| ---------------- | ------------- | -------------------------------------------------------------------------- |
| `fileName`       | `'data.csv'`  | The name of the downloaded file, used as it is given                       |
| `separator`      | `','`         | `','`, `';'` (what Excel reads where the decimal mark is a comma) or a tab |
| `values`         | `'formatted'` | `'formatted'` writes the text of the cells, `'raw'` writes the values      |
| `bom`            | `true`        | Starts the text with a byte order mark, so that Excel reads it as UTF-8    |
| `selectedOnly`   | `false`       | Only the chosen rows, among the ones the search and the filter keep        |
| `escapeFormulas` | `true`        | Puts a `'` before a text that a spreadsheet could run as a formula         |

An option outside its union (a `separator` of `'|'`, a `bom` of `'yes'`) is its default, with one
warning in development; the grid never throws for it.

**The rows** are the ones the grid shows after the search and the filter, in the order shown, and
**every page** of them, whatever the pager shows. The CSV is flat: no group row, no total row and no
detail row, and the rows of a closed group are in it, since a group only orders them. A row that is
kept by the search or the filter only because it has an unsaved change is in it, in the place the grid
shows it, and so is a row marked for deletion. A new row is not. A value is always the **saved**
one: a change that is not saved, in any edit mode, and a value being typed, are not in the CSV.
`selectedOnly` keeps the chosen rows among those; a chosen row that the filter hides is not exported,
and a grid with no chosen row, or with `selectionMode="none"`, gives the heading row alone.

**The columns** are the shown data columns in the order they are drawn: the left zone, the middle
and the right zone (see Pinned columns). A hidden column is not in it. A column the grouping takes
out of the table is written at its place in the layout, as if it were shown, so a grid grouped by
status still has the statuses. The columns the grid adds for itself (the boxes, the handles, the
buttons of the rows) are never written, and a column with `exportable: false` is left out. The first
record is the heading: the `caption` of each column, or its id.

**The values** of `'formatted'` are the text each cell writes: the column's Intl `format` with the
grid's `locale` and `timeZone`, the words of a lookup, `labels.yes` and `labels.no` for a boolean, the
text of a `format` function, and a computed column's text. A custom `cell` is written as its `text`,
not as what it draws. A blank is an empty field. The values of `'raw'` are: a number with a dot, a
`date` as `YYYY-MM-DD`, a `datetime` as ISO 8601 in UTC (`2026-11-05T17:30:00.000Z`), a boolean as
`true` or `false`, a string as it is, and a lookup by its value. A value its type cannot read is blank
in `'raw'`, as the cell is, except in a column whose own `format` function writes it: that column
writes the `format` text. The texts come through the same guard drawing uses, so a `format` or a
`value` that throws on a row of `data` throws from `exportCsv()` as it does when the cell is drawn.

**The format** is RFC 4180: a field is in double quotes when it holds the separator, a double quote,
a CR or an LF, or a space at its start or its end, and a double quote inside is doubled. Every record
ends with CRLF, the last one too. With `bom` the text starts with U+FEFF, which is what makes Excel
show Vietnamese letters correctly; where the decimal mark is a comma, `separator: ';'` makes Excel
split the fields. `escapeFormulas` is the guard against CSV injection (OWASP): a text of a `string`
column or a lookup, and a heading, that starts with `=`, `+`, `-`, `@`, a tab or a CR gets a `'`
before it, so a spreadsheet shows it as text. A number, a date and a boolean never get one, so a
negative number stays a number. In `'raw'` a lookup writes its value, which gets one unless it is a
number, a bigint or a boolean, whatever the column's `dataType`. Turn it off only for a file that no
spreadsheet will open.

**Server mode** (`remote`): `data` is the page, so the CSV holds the rows of the current page, in the
order the server gave, and `exportCsv()` warns once in development. Export the whole data on the
server. Nothing is announced after an export: the browser's download is the answer.

```tsx
const grid = useRef<DataGridHandle>(null);

<>
  <DataGrid
    ref={grid}
    data={orders}
    rowKey="id"
    columns={columns}
    caption="Orders"
    csvExport={{ fileName: 'orders.csv', separator: ';' }}
  />
  <Button
    onClick={() => {
      // The chosen rows, as text, with no download.
      const text = grid.current?.exportCsv({ selectedOnly: true });
      sendToMyApi(text);
    }}
  >
    Send the chosen rows
  </Button>
</>;
```

## Toolbar

The toolbar is the row above the grid: the caption block (see below), then the items of the grid:
`groupPanel`, the tray of the grouping (see The group panel), `spacer`, which takes the room
between the caption and the rest, `search`, the search field (see Search), `columnChooser`, the
button of the chooser, `exportButton`, the button that downloads the CSV (see CSV export), and
`addButton`, the button that adds a row (see Adding rows). The default order is the group panel, the
spacer, the search field, the chooser, the export button, the add button. The toolbar gets an item
for each part of the grid that comes with a control. The toolbar is drawn when it has a caption, a
description or an item.

- **`toolbar={false}`** takes the items away and **keeps the caption**, which names the grid (its
  `aria-labelledby`) and the pager. Without a caption or a description, the toolbar is not drawn.
- **`toolbar={(items) => …}`** is called with the items, and what it returns is drawn after the
  caption in place of the default ones: put the items in the order you want, and add buttons of
  your own. An item of a feature that is off is `null`; `spacer` is always there. A function that
  leaves `columnChooser` out leaves the button out, and no popover is mounted; one that leaves
  `search` out leaves the field out, and one that leaves `groupPanel` out leaves the panel out:
  the grid then has no tray to hold the chips of its grouping.

```tsx
<DataGrid
  columns={columns}
  data={orders}
  rowKey="id"
  caption="Orders"
  columnChooser
  toolbar={(items) => (
    <>
      <Button variant="ghost">Refresh</Button>
      {items.spacer}
      {items.columnChooser}
    </>
  )}
/>
```

## Caption and name

`caption` is the title of the grid, drawn above it by the element `captionAs` (`'h3'` by default,
the level of a `CardTitle`; `'h2'` to `'h6'`, or `'div'` for no heading), and it is the name of the
grid. `description` goes under it and is the description of the grid. They are drawn with the
classes of a Card header, in the toolbar, and without either of them, and without a toolbar item,
there is no space above the grid.

The grid has the `grid` role, and its name is, in order, an `aria-labelledby` you pass, the caption,
or an `aria-label` you pass. A grid with none of them warns once after it is mounted.
`aria-describedby` is yours joined to the description's, not replaced by it.

## Sorting

A column whose title is a button sorts. A press makes that column the only sort: ascending, then
descending, then no sort, which puts the rows back in the order of `data`. A press with Shift, or
with ⌘ on an Apple system and Ctrl on any other, adds the column as another level, and a second such
press turns it and a third takes it off, so that "Order date, then Total" is two presses. The keys
`Enter` and `Shift+Enter` on a button do the same. A press with a modifier does not select text.

```tsx
<DataGrid
  data={orders}
  rowKey="id"
  columns={columns}
  defaultSort={[{ field: 'date', direction: 'desc' }]}
/>
```

<Canvas of={Stories.Sorting} />

- **Which columns.** `allowSorting` is the default of every column (`true`), and a column's own
  `allowSorting` wins. A column that does not sort has a plain title: no button and no arrow, since
  an arrow would promise a control. `sortMode="single"` keeps one column: the modifiers do nothing.
- **How they compare.** Text with `Intl.Collator` in the grid's `locale`, with `numeric`, so "DH-2"
  comes before "DH-10"; numbers, dates and booleans as numbers; a column with a `lookup` by the text
  it shows. `sortValue(row)` replaces the value that the column is sorted by. A blank value is last,
  whichever way the column sorts, and rows that are equal keep their order.
- **What a screen reader gets.** `aria-sort` is on the heading of the first level only, since a
  table has one sorted column at a time. With more than one column sorted, every sorted title also
  says its place in hidden words, ", sorted descending, 2 of 3" (`labels.sortState`), and the number
  is drawn next to the arrow and hidden from a screen reader. After a press the grid says the whole
  sort, "Sorted by Order date, descending, then Total, ascending", or "Sorting cleared"
  (`labels.announceSort`, `labels.announceSortCleared`). It says nothing on mount, and nothing when
  a controlled `sort` changes from outside. What it says is the sort the press asked for: a
  controlled `sort` that you do not take is still heard as asked, though the heading shows yours.
- **A sort that is no longer true.** An item of `sort` whose `field` is not a column that sorts, or
  whose direction is not `'asc'` or `'desc'`, is left out without a warning: the state may come from
  what a person saved before the columns changed.

## Paging

The grid pages by default: `paging` is `{ pageSize: 20, pageSizes: [10, 20, 50, 100] }`. Under the
rows there is a bar with the count ("1–20 of 135"), the choice of how many rows a page holds, and
the pages. `paging={false}` is one page of every row and no bar. The bar is not drawn when there are
no rows. A page is counted from 0: `{ index: 0, size: 20 }` is the first.

<Canvas of={Stories.Paging} />

- **`pageSize` is the size at first.** A page that the grid holds starts at it; after that the size
  is the one the person chooses, and a later `pageSize` does not change it. A controlled `page`
  says its own size.
- **The choice of size** lists `pageSizes` and the size in use if it is not among them, in order,
  once each. Pass `pageSizes: []` for no choice.
- **A new size** keeps the first row that is shown: from the third page of 20, a size of 10 goes to
  the fifth page, whose first row is the row that was first. That is one `onPageChange`.
- **Sorting keeps the page.** A page that is out of range, because the data shrank or the state
  came from storage, is drawn as the nearest one, and no callback is called for that (in server
  mode the grid asks for it: see Server mode).
- **The name of the pages** is `labels.pagination` and the caption read together ("Pagination
  Orders"), so two captioned grids on a page have two landmarks that differ. A grid without a
  caption has `labels.pagination` alone: give each such grid its own.
- **`paging={false}` leaves the page state as it is held**, unused: `getState().page` is still
  `{ index: 0, size: 20 }` (or your controlled value), and it does not change when the data does. A
  state saved with paging off and restored with paging on behaves as `paging` says.

## Virtual scrolling

For a list too long to draw whole, pass `scrolling="virtual"` with a `height`. The grid then draws
only the rows near what is seen, and an empty box above and below stands for the rest, so the DOM
holds a few dozen rows however many there are, and the scroll bar is the one of the whole list. Ten
thousand rows are a few dozen `<tr>`.

<Canvas of={Stories.Virtual10000} />

- **`height` is required**, and it is the prop: a grid that has its height from a stylesheet alone
  scrolls as usual and warns once. The prop is also what the HTML from the server is made from: the
  first window is the rows that `height` shows and 6 more when it is a number of pixels, and 20 rows
  when it is a length (`'60vh'`).
- **What is drawn:** the rows that meet the frame, 6 more on each side so that a quick scroll finds
  rows there, and the row of the active cell, wherever the frame is scrolled. That row is never
  taken out, so the focus does not fall to the page when you scroll away from it, and the grid does
  not lose its one Tab stop. A spacer is a `tr` that is not a data row and is hidden from assistive
  technology. A scroll draws only the body, once a frame: the rows that come into the window, and
  not the heading, the caption or the rows that stay.
- **Rows have a fixed height**, so the window is arithmetic: the distance between two rows is the
  height of the table of the `density` and `variant`, measured on two neighbours once they are
  drawn. So what a cell holds must fit the row: a taller cell is not cut, it makes its row taller,
  and the rows after it are then drawn lower than the window counts, which drifts.
- **Group rows** are rows of the list with a height of their own: the one of the `density` and
  `variant` (8px less than a data row of the table), whatever `rowHeight` is. The window counts each
  kind at its height, with the one distance that is measured between two data rows, so a grouped
  list of ten thousand rows is as light as an ungrouped one. Opening or closing a group changes the
  list, and the window is made again from the rows that are there.
- **`aria-rowcount` and `aria-rowindex`** are set in a virtual grid, and only there: the table
  counts the heading, every row, group rows too, and the footer of totals when there is one, and
  each drawn row says its place (the heading is row 1, the footer the last), so a screen reader can
  say "row 5,000 of 10,001" for a row whose neighbours are not in the DOM. A data row inside a group also says `aria-setsize` and `aria-posinset` for its whole
  group, not for the part of it that is drawn. A grid whose rows are all drawn does not set them.
- **The keys go over every row:** <Kbd keys="mod+end" /> scrolls to the last row, draws it and
  focuses it, and the arrows and <Kbd keys="pagedown" /> past what is drawn do the same for their
  row. A page is the rows that fit under the heading, counted over their own heights, so a page that
  holds group rows has more rows than one of data rows alone. A group row with the focus is kept in
  the DOM like any other row.
- **No `renderDetail`:** a detail has no fixed height, so a grid with details scrolls as usual, with
  pages at the default size (`paging={false}` keeps one scroll), and warns once (see Master-detail).
- **No `paging`:** a virtual grid is one list. An object for `paging` is ignored with a warning
  (`paging={false}` is the same as leaving it out, and does not warn), and there is no bar.
- **Not in server mode:** with `remote` the grid has a page and not the list, so it scrolls as usual
  and warns once. Use the pages.
- **Stripes** follow the place of a row in the list, so they do not move as rows come and go.

### `scrollToRow`

`ref.current.scrollToRow(key)` brings the row with that key into view, by the least it takes, and
returns `true`. It returns `false` when no row has the key, or the filter takes it out, and does
nothing. A row inside groups that are closed opens them first, in one `onExpandedGroupsChange`
(then `onStateChange`), and then, in a grid with pages, goes to the page of the row. A step that
has to wait is a request pending until the grid's next commit, and for no longer: if that commit
shows the row, the grid scrolls to it; a parent that kept its groups closed or its page ends the
request. A parent that never re-renders after the change leaves the request pending, and the next
commit that comes for another reason ends it. It does not move the keyboard: the focus stays where
it was.
In a virtual grid it moves only the frame. In a grid with pages, or one that scrolls as usual, it
uses the browser's scroll into view, which scrolls the page too when the row is out of its sight.

## Server mode

With `remote` the grid sorts and pages nothing: `data` is the page, already in order, and the grid
draws it as it is. It counts `totalCount` rows in the bar, and a press on a title or on a page calls
`onSortChange` or `onPageChange` for you to load again. The header still shows the sort the press
asked for, and an uncontrolled sort and page are kept, so a grid that you do not control still
moves. Without `totalCount` the rows of `data` are counted, and the grid warns once.

<Canvas of={Stories.ServerMode} />

What the grid does not do in server mode: it does not sort or page `data`, and it cannot know
whether `data` is in the order its heading says. That is for the server to keep true. It does not
total the rows either: the footer of `summary.total` is drawn, and writes the values you give in
`totalSummary` (see Totals). Group totals are not drawn, and the grid warns once.

**A page past the last one.** When `totalCount` shrinks under the page you hold (page 6 of 20 rows,
and the server now says 30 rows), the bar shows the last page, and the grid calls `onPageChange`,
then `onStateChange` with `'page'`, once, with that page, `{ index: 1, size: 20 }`, for you to load
it: `data` is still the rows of the page that is gone. This is the one call of the grid that no
press makes; it comes after the render. It is made once for a page, a size and a `totalCount`, so
a parent that keeps its own page is not asked again, and a new `totalCount` that is still too small
asks again. It is made only once the load is over and `totalCount` is given: a page you restore
from the address or a saved state, before the server has answered, is not asked away. Without
`remote` the grid has the rows, shows the last page, and calls nothing.

## Selecting rows

`selectionMode` is `'none'` (the default), `'single'` or `'multiple'`. With either of the others
every row has `aria-selected` (`true` or `false`), and a chosen row has the look of a chosen row of
a Table: the wash of the accent, and in a `lined` grid the bar of 3px on its first cell.

<Canvas of={Stories.Selecting} />

- **`single`** has no boxes. A press on a row chooses it, and so does Space on one of its cells; the
  row that was chosen is not. Pressing the row that is chosen leaves it chosen, and calls nothing.
  A saved `selectedKeys` of several keys draws each of their rows chosen, and the next press or
  Space keeps one.
- **`multiple`** adds a first column of 40px with a box in each row, and a box in its title. The box
  of a row is named `labels.selectRow(name)`, where `name` is the text of the row header (the column
  with `rowHeader`, whether it is drawn, hidden or grouped by) or, without one, the key. The grid
  has `aria-multiselectable`. Only the box chooses a row, unless `selectOnRowClick` is `true`, which
  makes a plain press on the row do what its box does. In a cell the box is the one stop of Tab, and
  Space and Enter act on it (Enter presses it, as it would a button).
- **The box in the title** chooses the rows of its scope, or takes them off when they are all
  chosen, and is mixed when only some are. With `selectAllMode="page"` (the default) the scope is
  the rows of the page that is shown, and the box is named `labels.selectAllOnPage`; with `"all"` it
  is every row after the sort, and `labels.selectAll`. With no row in its scope the box is disabled,
  and the title takes its place as the stop. When rows come or go while the title or its box has the
  focus, the focus moves to the one that is the stop now, so the keys go on. Space and Enter press
  the box, as they do the box of a row. In server mode the grid has only the page, so `"all"` is
  `"page"` there, and the grid warns once.
- **A range.** A press with Shift on a box or on a row, or Shift+Space on a cell, adds the rows from
  the anchor to that row, in the order shown (the sort, across pages). The anchor is the row last
  chosen by a plain press or Space; the range does not move it, and does not take anything off. A
  Shift press does not start a text selection.
- **Keys.** Space on a cell of a row chooses it (`multiple`: toggles it), Shift+Space chooses a
  range, and mod+A (⌘+A on an Apple system, Ctrl+A elsewhere), with the focus in the rows or the
  titles, chooses every row of the scope, and the page's text is not selected (in a grid with no row
  it only cancels the key); Ctrl+A is left to the browser on an Apple system, and mod+A is left to
  it in a grid that is not `multiple`. A is the letter the key types, or, on a layout that types no
  Latin letter there (Russian, Greek), the key where QWERTY has it, as for the browser's own
  shortcuts.
- **A press on a control in a cell does one thing.** A link, a button, a field or the box of the
  row is the control's own press: it never also chooses the row through `selectOnRowClick`.
- **The keys are kept**, not the rows: a sort, a page or a change of `data` does not take away what
  is chosen, and a row that leaves `data` stays chosen, and shows chosen again if it comes back.
  `selectedKeys` that name no row are left as they are, with no warning (they may come from a state
  you saved).
- **Said after a range, a select all and mod+A:** `labels.announceSelected(count)`, the count of the
  chosen keys after it ("5 rows selected"). It is the count the press asked for: a controlled
  `selectedKeys` that you do not take is still heard as asked.

```tsx
<DataGrid
  data={orders}
  rowKey="id"
  columns={columns}
  caption="Orders"
  selectionMode="multiple"
  onSelectedKeysChange={(keys) => setChosen(keys)}
/>
```

A `cell` is told `selected`, whether its row is chosen. A choice draws again only the rows it
changes.

## Filtering

The filter is the search and the conditions of the columns. Its state is a value of the grid, as the
sort is: `filter`, `defaultFilter` and `onFilterChange`, controlled or not. The search field is
described in Search below, the cells that set the conditions in The filter row, the funnels in The
header filter and the conditions in words in The filter panel. What this section
says is what the state holds and what a change of it does.

```tsx
const [filter, setFilter] = useState<DataGridFilter>({
  search: 'minh',
  columns: { status: { values: ['cancelled'], exclude: true } },
});

<DataGrid data={orders} rowKey="id" columns={columns} filter={filter} onFilterChange={setFilter} />;
```

**What the state holds.** `search` is a text that a row must hold, in the formatted text of a shown
column, whatever its case or accents. `columns` is by column id, and each column has up to two
conditions that are joined by "and": the one of its filter row (`operator` and `value`) and the one
of its header filter (`values`, and `exclude` to keep the rows that are not in them).
`enabled: false` puts the conditions of the columns aside and keeps the search. A value is what JSON
holds: a string for text, a number, an ISO day `YYYY-MM-DD` for a `date` and for a `datetime` (its
day in the zone its cells are shown in), a boolean, the value of an item of a lookup, and
`[from, to]` for `between`.

**What is ignored.** A filter is shown as it is given. A condition of a column the grid does not
have, an operator the column does not offer and a value it cannot read filter nothing and stay in
the state: a filter that was saved, or that comes before its columns (`defaultFilter` names a column
that a request brings later), does no harm and applies when its column arrives. A part of the wrong
kind (a `search` that is not a string, a `values` that is not an array) is left out, and the prop
warns once.

**What a change does.** A change that a person makes calls `onFilterChange` with the new filter and
then `onStateChange(state, 'filter')`, once for each change, never for a render or for a `filter`
that you change from outside; a filter that says what the grid holds already is no change. A change
takes the grid to its first page: when the page was not the first,
`onPageChange({ index: 0, size })` and `onStateChange(state, 'page')` follow, so a controlled page
hears of it. Then the grid says how many rows are left, `labels.announceRowsFound` ("12 rows", "1
row", "No rows"), through its live region 500 ms after the last change, so a search that is typed
says it once. Nothing is said when the grid mounts, or for a filter that changes from outside, or
for a parent that keeps its own filter. A change that keeps the same rows, such as a space typed
after the search, is stored and reported as typed (the field keeps its text), but it neither goes
back to the first page nor says the rows found.

`ref.current.clearFilter()` clears the search and every condition, as the button of an empty grid
does: `enabled` goes back to its default too, so the next condition is not put aside behind a
switch. It calls the callbacks as a press does, goes to the first page and says the rows found. It
does nothing when the grid has no filter.

**An empty grid because of its filter.** When no row is left and the grid is filtering, the grid
says `labels.noMatches` ("No rows match the filter") under a ring with a funnel crossed out, with a
`Clear filter` button (`labels.clearFilter`) that clears the filter. The box is the one of
`labels.noData`. The button is the one place of the body: ↓ from a title reaches it, ↑ goes back to
the title of the column the place was at, Enter and Space press it, and the grid has the one Tab
stop all the same. When the filter is cleared the rows come back and the place is the first cell of
the first row, with the focus if it was on the button.

**Server mode.** With `remote` the grid filters nothing: `data` is the page that your request
brought, and `onFilterChange` is how you learn what to ask for. Load from one effect on the state
(`onStateChange`, or `filter`, `sort` and `page` together), and pass `loading`: set it in the same
render as the state that asks for the request, not in the effect that starts it, or the render in
between says "No data" (or "No rows match the filter") in an empty cell until `loading` comes. The
rows found are `totalCount`, said once for each change, 500 ms after the rows that you asked for
have come: the first render after the change where `loading` is not `true` and either `data` is
another array or the grid was loading in between. So a grid says the count when its `loading` ends,
or when new rows come, whichever is first. Keep `data` the same array until your rows come, or it
is taken for them.

## The filter row

`filterRow` puts a row of cells under the titles, one for each column that filters. It is a row of
the heading, so it sticks with the titles, and it is a row of the grid for the keyboard (see
Keyboard). A column whose `allowFiltering` is `false` (the grid's `allowFiltering` is the default)
has an empty cell there, and so has the column of boxes. Any value of `filterRow` other than `true`
is `false`.

```tsx
<DataGrid data={orders} rowKey="id" columns={columns} caption="Orders" filterRow />
```

**The cells.** A column of text has an input, named `labels.filterCell(caption)` ("Filter
Customer"), with the button of its operator at the start. A boolean and a column with a `lookup`
have a Select with no operator: its first item, and its placeholder, is `labels.all` ("(All)"),
which takes the condition away, and then come the two words of a boolean (`labels.yes` and
`labels.no`) or the items of the lookup, in its order. A column of numbers has an input too, written
from the end, which reads what is typed as the grid's `locale` writes a number (`1,000.5` in
`en-US`, `1.000,5` in `vi-VN`) and shows a held number the same way, with no grouping. The
separators of another locale read as another number: `1.5` in `vi-VN` is 15, and the two ends of a
range are read the same way. Text that is no number marks the input invalid and stays as typed; the
state holds numbers only, so it is applied as no value: the condition the column had goes (once, and
only if it was there), and a number typed after it comes back. A column of days (`date`, and
`datetime`, which is filtered by its day in the zone its cells are shown in) has the
[DatePicker](?path=/docs/components-datepicker--docs) of the library, with the button of its
operator as its `startContent`, its own calendar button, and the locale of the grid. A day applies
when it is picked in the calendar, and when the typed text is left or Enter is pressed, with the
operator the user chose; emptying the text takes the value away. Text that is no day is treated as a
number cell treats text that is no number: the picker shows its own fault, and the condition the
column had goes (once, and only if it was there), while the text stays as typed. The frame is marked
invalid and the field is described by the picker's error, which is visually hidden in a filter cell so
that the filter row does not grow.

**When a condition applies.** What is typed in an input becomes the condition of the column 400 ms
after the last key; while an input method composes nothing is sent, and the 400 ms start when the
composition ends. Enter applies it at once (unless an input method is composing), and so does
leaving the input, which pressing the button of the operator does. A condition that is emptied is
taken away. Esc in an input that holds text, a day included, clears it and applies that at once, and
the grid does not take the key; Esc with no text is the grid's, and goes back to the cell. A choice
in a Select applies at once, with `=`; so does a day. A condition that changes from outside (a
controlled `filter`, `clearFilter()`) replaces the text and drops one that was waiting; a clear does
the same for a text typed when the filter held no condition for the column. Typing draws the input
and nothing else. Every change goes through the path of every change of the filter:
`onFilterChange`, `onStateChange(state, 'filter')`, the first page and the rows found (see
Filtering).

**The operators.** The button shows the glyph of the operator the column filters by, and is lit
while the column's condition of the row filters. A press opens the one menu of the grid, under the
button, with the operators of the column: for text `contains` (the default), `notContains`,
`startsWith`, `endsWith`, `=` and `<>`. The chosen one is checked and has the focus; a choice
applies at once, with the text of the cell, and the focus goes back to the button, or to the one
that stands for it when the choice swapped the cell's control (to or from `between`). The menu
closes when its column is hidden. An operator with no text is kept in the state, so the cell shows
it, and filters nothing until there is some. A column's `filterOperators` narrows the list, in the
order of its type, and the first of those is the default. The words come from `labels.operators` (a
record that you may give in part: the operators you leave out keep their English words), the name of
the button from `labels.operator(name)` ("Operator: Contains").

**Numbers and days.** They offer `=` (the default), `<>`, `<`, `>`, `<=`, `>=` and `between`. A
value does not move from one operator to another, except across `between`: a range is two ends and
not one value, so going to it or from it leaves the cell with no value, and its operator.

**A range.** With `between` the cell is a read-only field that says the range: with both ends,
`labels.range(from, to)`, each end written as the column writes it; with one end only, `≥` or `≤`
and that end (`≥ 5`, `≤ 31/10/2026`, the words of `labels.panelOperators`); `labels.between` when
there is none. A press on it, or Enter, opens the one popover of the grid under it: two fields,
named `labels.from` and `labels.to`, with a number input or a DatePicker, and `labels.cancel` and
`labels.ok`. It starts from the ends the condition holds. OK, or Enter in a field, applies
`[from, to]` (`[from, null]` for an open end; both empty is no value) and closes it; a number or a
day that cannot be read keeps it open, with the focus on that field. Ends that are read are applied
as typed, an inverted range too: `[21, 12]` shows as "21 – 12", and no row matches. Cancel, Esc and
a press elsewhere close it and change nothing. Tab past OK and Shift+Tab before the first field
close it the same way and give the focus back to the field. The popover is the glass popover of the
library with its arrow, a `dialog` named `labels.filterCell(caption)`, drawn after the table (one
for the whole grid) and only while it is open; its keys and its presses are not the grid's, and
opening it scrolls neither the page nor the frame. It closes when the operator of its column stops
being `between` by a change from outside (`clearFilter()`, a controlled parent), and the focus goes
to the cell's operator button.

**The keys.** The filter row is a row between the titles and the rows: ↑ from the first row goes to
it, and then to the titles. A cell holds the focus itself, and Enter or F2 goes into its input, its
DatePicker or its Select, not into the operator; Tab goes round the controls of the cell, and Esc or
F2 comes back. The keys of a column (Enter to sort, resizing, moving, the menu) are the keys of its
title alone. In a virtual grid the titles are row 1, the filter row row 2 and the first row of data
row 3.

## The header filter

`headerFilter` puts a funnel on the title of each column that has one: it opens a list of the values
that the column holds, each with a box, and what is checked is kept. A column whose
`allowHeaderFiltering` is `false` has no funnel (the grid's `allowHeaderFiltering` is the default,
`true`), and neither has the column of boxes. Any value of `headerFilter` other than `true` is
`false`. It is a button of the title, after the sort button and before the one of the column menu,
and it is always drawn. It is filled while the column has a condition of its header filter, and a
condition of the filter row does not fill it. Its name is `labels.filterColumn(caption, active)`.

```tsx
<DataGrid data={orders} rowKey="id" columns={columns} caption="Orders" headerFilter />
```

**The list.** The popover is the one popover of the grid, the glass popover of the library with its
arrow, a `dialog` named `labels.filterColumn(caption, false)`, drawn after the table and only while
it is open, under the funnel and centred on it, 216px wide. It holds a search field
(`labels.searchValues`), the list, and `labels.cancel` and `labels.ok`. The list has
`labels.selectAllValues` first, which checks what the search shows, then the values of the column as
the column writes them and in the order the column sorts, and `labels.blank` last when a row is
blank. A `datetime` column lists its days, in the order of the days: a `sortValue` orders its rows
and not its list. Nine values show; the list scrolls after that, and past 500 values only the first
500 are drawn, with a line, `labels.moreValues(shown, total)`, to say so: search to narrow them.
The search narrows the list at once, whatever the case or the accents.

The values are those of the rows that the search of the grid and the conditions of the other columns
keep, so each list is narrowed by what is already filtered, with the values that the column's own
condition names added. A column's own conditions do not narrow its own list. The list is read when
the popover opens, and it does not change while the popover is open.

A column that has `headerFilter.values` lists those, in its order and with its texts, in a client
grid too: no row is read, and neither the search nor the other columns narrow them. Only the values
that the column's own condition names and the list lacks are added. The rows of a client grid may
hold values that the list does not name, which the user never saw, so such a list always counts as
narrowed for OK (see OK).

**OK.** The boxes start from the column's condition, all checked when it has none. OK stores what is
checked as the header condition: every value checked is no condition, more than half checked is
`exclude` with the values that are not checked, and the others are `values` with the ones that are.
When the list is narrowed (by the search or by the conditions of other columns, in a client grid by
a column's own `headerFilter.values`, or in server mode by the page it lists) the values it does not
show are left as they were: a `values` condition stays
`values` with the checked ones, all of them too, and any other becomes `exclude` with the unchecked
ones, which is no condition when none is unchecked. An OK with the boxes as they were when the
popover opened changes nothing, as Cancel. Nothing checked is a condition that keeps no row, and not
a change that is left out. The condition of the filter row of the column stays, and the two are
joined by "and". OK calls `onFilterChange` once, goes to the first page and says the rows found.
Cancel, Esc and a press elsewhere close the popover and change nothing, and an OK that changes
nothing calls nothing.

**The keys.** Enter on the funnel opens it, with the focus in the search field. ↓ in the search
field goes into the list, which is one stop of Tab: ↑ and ↓ move among its boxes, Home and End go to
the first and the last, and Space checks. Enter, but not on a button, is OK. Tab past OK and
Shift+Tab before the search field close the popover as Cancel does and give the focus back to the
funnel. A second press on the funnel of the open popover closes it, and a press on the funnel of
another title moves the popover there. Turning `headerFilter` off (or the column's
`allowHeaderFiltering`) while it is open closes it for good, as turning `filterRow` (or the column's
`allowFiltering`) off does for a range; the focus goes to the grid, and turning the feature back on
opens nothing. Opening it scrolls neither the page nor the frame. F2 on a
title goes into its controls in the order of the title: the sort button, the funnel, the menu.

**Server mode.** With `remote` the grid cannot know the values of the rows it has not got, so the
list is the column's `headerFilter.values`, in its order, each with its `value` and its `text`. A
column that allows header filtering and has none lists the values of the page and warns once.

```tsx
const columns = [
  {
    field: 'status',
    caption: 'Status',
    headerFilter: {
      values: [
        { value: 'new', text: 'New' },
        { value: 'processing', text: 'Processing' },
      ],
    },
  },
];
```

## The filter panel

`filterPanel` draws a bar between the grid and its pager that says what the filter is, in words,
with a button that clears it and a switch that puts the conditions aside. Any value of `filterPanel`
other than `true` is `false`.

```tsx
<DataGrid data={orders} rowKey="id" columns={columns} caption="Orders" filterRow filterPanel />
```

**When it is there.** The panel is drawn while some column has a condition that filters, and the
search alone does not make one. It stays when the switch has put the conditions aside, so the person
can turn them on again, and it goes with the last condition. It is outside the table, 14px from the
grid and from the pager, and it is two stops of Tab after the grid: Clear filter, then the switch.

**The words.** Each condition is the caption of its column in semibold, then what it asks. The
conditions of the filter row come first and those of the header filter after them, each in the order
of the columns: the left zone, the middle, the right zone, and the columns that are hidden last,
because a hidden column goes on filtering. A column that has both has two. "and" (`labels.and`) is
muted and stands between them. The words wrap, and are never cut.

| Condition                     | Is said as                                  |
| ----------------------------- | ------------------------------------------- |
| text with an operator         | `Customer contains ‘ltd’` (`labels.quoted`) |
| a number, a day, a lookup     | `Qty > 5`, `Order date ≥ 05/11/2026`        |
| `between` with both ends      | `Qty 5 – 9` (`labels.range`)                |
| `between` with one open end   | `Qty ≥ 5`, `Order date ≤ 31/10/2026`        |
| a header condition            | `Status is any of (New, Processing)`        |
| a header condition, `exclude` | `Status is none of (Cancelled)`             |

The operators are the words of `labels.panelOperators` (`=`, `≠`, `<`, `>`, `≤`, `≥`, "contains",
"does not contain", "starts with", "ends with"), a record that may be given in part; `between` is
not one, since a range is said with `labels.range` or with `≥` or `≤`, and so is the field of a
range in the filter row. A value is written as its column writes it, a lookup by its text, a boolean
by `labels.yes` and `labels.no`, a blank by `labels.blank`. A header value is written by the
`text` that the column's `headerFilter.values` gives it; otherwise, for a column with a `format`
function, by the text of the first row of the grid's `data` that holds it (the page, in server
mode), as the cells and the header list write it, and a value that no row holds is written as its
key.
`labels.isAnyOf` and `labels.isNoneOf` say a header condition.

**Clear filter.** The button clears the search and every condition, and `enabled` with them, as
`clearFilter()` does: one `onFilterChange`, the first page, the rows found. The panel goes with the
filter, and when the focus was on the button it goes to the active cell of the grid, and never to
the page.

**Apply filter.** The switch is `filter.enabled`. Turned off, the grid shows every row that the
search keeps, the panel stays, and the cells of the filter row and the funnels go on showing the
conditions that were put aside. It is a change like any other: one `onFilterChange` with
`enabled: false`, and turning it on takes the key away instead of writing `enabled: true`. Its name
is `labels.applyFilter`.

## Search

`searchPanel` puts a search field in the toolbar, after the spacer and before the column chooser:
a search field of the library, 260 px wide, named `labels.search` ("Search") and with the
placeholder `labels.searchPlaceholder` ("Search…"). `searchPanel={{ placeholder: 'Find an order' }}`
brings a placeholder of its own; any value other than `true` and an object is `false`, which draws
no field. On a screen narrower than 640 px a toolbar with the field gives the caption the whole row,
and the field fills the row below it.

```tsx
<DataGrid data={orders} rowKey="id" columns={columns} caption="Orders" searchPanel />
```

**What it does.** What is typed becomes `filter.search`, 300 ms after the last key; while an input
method composes nothing is sent, and the 300 ms start when the composition ends. Enter applies it at
once (unless an input method is composing), and so do Esc, the clear button and leaving the field,
which also apply a text that is still waiting. The field keeps what is typed, spaces and all; the
grid trims it. Typing draws the field and nothing else, so a grid of many rows does not draw on
every key. A search that changes from outside (a controlled `filter`, `clearFilter()`) replaces the
text and drops one that was waiting, and so does a clear (`clearFilter()`, the button of the empty
grid or of the panel), which says there is no search even when the filter held none. A parent that
keeps its `filter` as it was (it ignores `onFilterChange`) leaves the field showing the text that
was typed, which the filter does not hold: the field changes again only when the filter does. A
change goes through the same path as every change of the filter: `onFilterChange`,
`onStateChange(state, 'filter')`, the first page and the rows found (see Filtering).

**What is searched.** The search keeps the rows that hold the text in at least one shown column,
reading the text that the column shows (formatted dates and numbers, a lookup's display text, a
boolean's words), without regard to case or accents: "duong" finds "Đường" and "đường", and `đ` is
`d`. A hidden column is not searched, and a column with `allowSearch: false` never is. A search of
nothing but spaces keeps every row.

**The marks.** The grid wraps every match in a `<mark class="flg-data-grid-match">`, in the letters
the text has, in each cell that it draws as text: strings, numbers, dates, the text of a lookup and
the words of a boolean that a `format` or a lookup writes. It marks the same cells that it searches:
a column with `allowSearch: false`, and the hidden words of the check of a boolean, have no marks. A
`cell` draws what it likes; `ctx.highlight(text)` gives it the marks for any text it shows, and the
text as it is when the column does not allow search or there is no search:

```tsx
{ field: 'assignee', cell: ({ text, highlight }) => <strong>{highlight(text)}</strong> }
```

A match is a pill in the highlight colours and bold; in a chosen row, whose wash is the same colour,
only the bold shows. With high contrast the match is solid, and with forced colours it takes the
system's `Mark` colours.

**Server mode.** With `remote` the grid filters nothing and only reports the search; it marks the
page that `data` holds.

## Grouping

`grouping` is a list of levels, outermost first: `{ field, direction }`, where `field` is the id of a
column and `direction` is `'asc'` or `'desc'` (the order of the groups of that level). It is state
like the sort: `grouping`, `defaultGrouping` and `onGroupingChange`, and `onStateChange` hears it
as the part `'grouping'`. A grouped grid is a **tree grid**: the table has `role="treegrid"`, and
each group is a row of its own.

```tsx
<DataGrid
  data={orders}
  rowKey="id"
  columns={columns}
  caption="Orders"
  defaultGrouping={[
    { field: 'status', direction: 'asc' },
    { field: 'assignee', direction: 'asc' },
  ]}
/>
```

A **group row** says the name of the column, the value of the group and its number of rows, "Status:
Delivered (4)", with a chevron that says whether the group is open. The value is written as the
cells write it (a lookup's text, a formatted number, a day in the grid's `locale` and `timeZone`),
and a blank value is the group `labels.blank`, which comes last in both directions. The groups of a
level come in the order of the funnel's list for that column, which is the order the column sorts
by. A press anywhere on a group row opens or closes it, and a double press does it once. The rows
inside it are one level deeper: `aria-level` counts the levels of the grouping and one more, and
`aria-setsize` and `aria-posinset` say a row's place in its group.

Each level of the grouping has an **indent column** of 28px after the column of boxes and the column of row handles; one cell in
the heading stands over them all, and over the column of the detail buttons when there is one (see
Master-detail), with the hidden words `labels.groupsAndDetails`. An indent column
is part of the layout (it has a width and is pinned with the first pinned column) and never a place
of the keyboard. A column the grid groups by leaves the heading, the rows, the filter row and the
funnels, since its value is in the group rows: its conditions still filter, it keeps its place, width,
pin and `hidden` in the layout, and it comes back when the grouping goes. Say `showWhenGrouped: true`
on a column to keep it in the rows too. If the grouping would leave no column, the first grouped
column stays. The column chooser lists every column the grouping has not taken out, hidden ones
included, and the filter panel says the conditions of a grouped column after the shown ones, in the
order of the grouping, before the hidden ones. A grouped column is searched as if it was shown, and
its group rows mark a match in the value.

### Open and closed

`expandedGroups` says which groups are open: `{ allExpanded, except }`. With `allExpanded: true`
every group is open but the ones in `except`; with `false` every group is closed but the ones in
`except`. It is state too: `expandedGroups`, `defaultExpandedGroups` and `onExpandedGroupsChange`,
and `onStateChange` hears the part `'expandedGroups'`. Groups start open; `autoExpandAll={false}`
starts them closed, and `defaultExpandedGroups` wins over it. `autoExpandAll` is read once, as a
default is. `ref.current.expandAllGroups()` and `ref.current.collapseAllGroups()` open and close
every group, and call nothing when that is what is held.

A **group key** is the JSON text of the `[field, value]` steps from the outermost level down to the
group, the value being the one the filter holds for the column: a day as `YYYY-MM-DD` for a `date`
and a `datetime` (in the grid's `timeZone`), a lookup's raw value, `null` for the blank group. A key
holds the levels above it, so the same value under two parents is two groups. A key that no group
has is ignored and stays in the state, as does an item of `grouping` that names no column, a
column that does not allow grouping or a field that came before: they group nothing and say nothing,
since a state from a person's storage may hold them. A column that comes after the mount groups when
it arrives, if `defaultGrouping` names it. A `grouping` that is not an array, or an item that is not
an object, warns once and the rest is kept.

### Pages, choosing and server mode

The pager counts the group rows and the data rows: "1–20 of 52" counts both. A page may start inside
a group; it then begins with that group's row again, with `labels.continued` after it, and that row
is the group's own (it opens and closes it). A change of the grouping goes to the first page, which
calls `onPageChange` once more when the page was not the first; a press that opens or closes a group
keeps the page, except when a group closes under the active place and its own row is on another page
(the place was on its repeat, or on a row of it): the grid then goes to the page of that row, as a
second change with its own `onPageChange`, and the focus is on the group's row. A group row has no box. "Select all" chooses the data rows of the page, or every row
after the filter with `selectAllMode="all"`, the rows of closed groups too; a range from Shift
is taken over the data rows that are shown, so the rows of a closed group are left out of it.

With `remote` the grid does not group: `data` is the page, so the grouping is held, ignored and
warned about once. Group on the server and send the rows as they are to be shown.

## The group panel

`groupPanel` puts a tray in the toolbar, before the search field (`false` when left out): a group
named by `labels.groupPanel` that holds the grouping as chips. Its first word is
`labels.groupBy`, then a chip for each level in order, with a chevron between two of them. It is as
wide as its content. Empty, it says `labels.groupPanelHint` beside the group icon. In server mode
the grid groups nothing, so it draws no panel and warns once. A `toolbar` that leaves
`items.groupPanel` out, or `toolbar={false}`, has no tray either, and then the grid offers no grouping
by the menu of its columns or by a drag of a title either: a user who grouped there could not
ungroup, since a grouped column leaves the heading and the chooser and there would be no chip. The
grouping is then the app's (`grouping`, `defaultGrouping`).

```tsx
<DataGrid
  data={orders}
  rowKey="id"
  columns={columns}
  caption="Orders"
  groupPanel
  defaultGrouping={[{ field: 'status', direction: 'asc' }]}
/>
```

A **chip** is the caption of the column and two buttons: the first turns the direction of its level
(its name says the next one, `labels.groupDirection(caption, next)`, and nothing else is said), the
second takes the level out (`labels.ungroup(caption)`, and `labels.announceUngrouped` says it). The
buttons are stops of Tab of the toolbar, two for each chip, in the order of the levels. After a
removal the focus goes to the same button of the chip that is now in its place, else of the chip
before, else to the active cell of the grid.

There are three ways to put a column in the grouping, and each is one change: `onGroupingChange` and
`onStateChange` are called once, the page goes to the first when it was another one (a second pair
of callbacks), and what was done is said (`announceGrouped`, `announceUngrouped`,
`announceGroupMoved`).

- **The menu.** "Group by this column" in the menu of the column (see The column menu) adds the
  level at the end, ascending.
- **Drag a title into the panel** with a mouse or a pen. The level goes where the pointer is over
  the chips: before the chip whose half the pointer is in, or after the last. While a title is over
  the panel the border of the panel is the accent, a bar of 3px shows where the level would go, the
  heading has no drop line, and the frame is not scrolled. A column that cannot be moved in the
  heading is still dragged into the panel when it allows grouping; a column that is grouped by
  already, and the last data column shown unless it stays shown when grouped (`showWhenGrouped`),
  do not mark the panel and a drop changes nothing.
- **Drag a chip** with any pointer (the chips are on the toolbar, which does not scroll, and have
  `touch-action: none`, so a finger moves them too). Over the panel the bar shows the new place and
  a drop moves the level there (a drop beside the chip itself changes nothing); over the headings a
  drop ungroups, and the column comes back to its place of the layout; anywhere else a drop does
  nothing. A press on a button of the chip is the button's and starts no drag. The source chip is
  dimmed to 35% and the grid's one chip follows the pointer. <Kbd keys="esc" />, `pointercancel`, a
  lost capture, the panel being turned off and the grid going all end the drag the same way, and
  take off what it set (the bar, the border, the dim, the cursor of the page).

<Kbd keys="mod+shift+left" /> and <Kbd keys="mod+shift+right" /> on either button of a chip move its
level one place (`announceGroupMoved`, "Status moved to grouping level 2 of 3"); at an edge the key
is cancelled and nothing changes. The focus stays on the same button of the same chip.

With a forced-colours palette the tray is drawn with the system's border and background, a chip has
a 1px border and its buttons are the colour of a button, and the border of the tray and the bar
that show a drop are `Highlight`.

## Totals

`summary` asks for totals. `summary.total` is the footer of the grid and `summary.group` is the
totals on the group rows. Each item names the column it is shown under (`column`), and what it adds
up (`type`):

- `'count'` is the number of rows, always a whole number.
- `'sum'` and `'avg'` read the finite numbers of the item's `field` (the column's own when
  `field` is left out) and skip the rest. The sum of nothing is 0, the average of nothing is blank.
- `'min'` and `'max'` read the numbers, dates and datetimes of `field` and are blank for a column
  of any other type. They are written as the cell of the row that holds the value is written.
- A function of the rows is called once for the rows and its result is shown, written as a string.

`label` says the words before the value; without it the grid says its own word for the type
(`labels.summary`: Count, Total, Average, Min, Max), so a group row says "Total: 65.720.000 ₫".
`format` writes the value, as Intl number options or as a function; without it a `sum` or an `avg`
is written as the column writes a number (its Intl options, else the `locale`). A function needs a
row and a total has none, so a total of a column whose `format` is a function is written by the
item's own `format`, else by the locale: give the item a `format`. Items of one column come in the
order given. An item that draws nothing warns once, and each cause has its own words: an item that
names a column the grid does not have (where it is shown, or the `field` it reads), and an item whose
`type` is none of the five and no function. Of two items with one `id` (the id they have, else
`type:field`) the first stays and the grid warns once, and says to give the item an `id`.

```tsx
const summary = {
  total: [
    { column: 'id', type: 'count', label: 'Orders' },
    { column: 'qty', type: 'sum' },
    { column: 'total', type: 'sum' },
  ],
  group: [{ column: 'total', type: 'sum' }],
} satisfies DataGridSummary<Order>;

<DataGrid data={orders} rowKey="id" columns={columns} caption="Orders" summary={summary} />;
```

**On a group row** the caption goes on up to the column before the first one that has a total, and
never past the end of the left zone, where it stops and is pinned with the zone; the band goes on in
an empty cell. Then each column has a cell of its own, with its total or empty, pinned as its column
and aligned as its column. A total of a column the caption covers (the first data column) is written
in the caption, after the count. A total is its label, muted and regular, and its value, semibold,
and does not wrap.

**The footer** is Table's footer of the variant, one row under the body, and is drawn whenever
`summary.total` has an item: it stays while a filter leaves no row, and is left out only while the
first rows load. It adds up every row after the search and the filter, of every page and of the
groups that are closed. Its cells do not wrap. A total with a `label`, or one that is not a `sum`,
says its label and the value ("Orders: 12"); a `sum` with no label is the value alone, with the
hidden words `labels.summaryOf` ("Total of Qty") before it so that it reads on its own, with the
caption of the column it reads (`field`), which may not be the one it stands under; a function type
says the caption of the column it stands under. With a `height` the footer sticks at the bottom of the
frame, as the heading sticks at the top, over a solid colour, with its pinned cells solid too; the
grid measures it, and every row and cell keeps that much scroll margin at the bottom, so what
scrolls into view stops above it. Without a `height` the footer is Table's, at the end of the rows.

The footer is a row of the keyboard, as the filter row is: each cell has `tabindex` (the box, the
handle and the detail column have an empty one, the group indents one between them). <Kbd keys="down" /> from the last row of the list
lands on it, in the column the place was in, and <Kbd keys="up" /> goes back to the last row;

<Kbd keys="left" />, <Kbd keys="right" />, <Kbd keys="home" /> and <Kbd keys="end" /> go along it;
<Kbd keys="mod+end" /> and <Kbd keys="pagedown" /> stop at the last row of the body, and
<Kbd keys="enter" />, <Kbd keys="f2" /> and <Kbd keys="space" /> do nothing in it (Space is
cancelled). A grid with no row has no footer place; the empty cell stays its one place.

**Server mode.** The grid does not total the page. The footer writes `totalSummary[id]`, the value
the server computed for each item, by the item's `id`; an id with no value of its own (an id
`constructor` holds nothing inherited) is blank. Each value is written by the item's `format`,
else as the column writes it, a `count` as a whole number and a function's as a string. The value of
a `date` or `datetime` column is read as its cells read a value (an ISO string, an epoch number or
a `Date` for a `datetime`; an ISO day or a `Date` for a `date`) and written with the column's own
format and zone; a value the column cannot read is blank.

## Master-detail

`renderDetail(row)` gives each row a detail: a row that opens under it and holds what the function
returns. The grid then has a column of 40px with a button for each row, after the column of boxes and
the indent columns of a grouping, and the button opens and closes the detail of its row.
`rowHasDetail(row)` takes it away from some rows: such a row has an empty cell where the button would
be. Without `rowHasDetail` every row has a detail. A value that is no function (`false` from
`cond && fn`, say) is none: it warns once and every row has a detail; a `renderDetail` that is
defined and no function warns once and the grid has no details.

<Canvas of={GroupingStories.GridGroups} />

```tsx
<DataGrid
  data={orders}
  rowKey="id"
  columns={columns}
  caption="Orders"
  renderDetail={renderOrderDetail}
  rowHasDetail={hasLines}
  defaultExpandedRows={['DH-1024']}
/>
```

`renderDetail` and `rowHasDetail` are read by every row, so write them outside the component or in
`useCallback`: after three renders in a row with a new one the grid warns.

**The state** is `expandedRows`: the keys of the rows whose detail is open, in the order they were
opened. It is controlled or uncontrolled like the rest (`expandedRows`, `defaultExpandedRows` and
`onExpandedRowsChange`), and `onStateChange` hears it as the part `'expandedRows'`. The keys are
compared as a set: the same keys in another order, or a key twice, is no change. A key that no row has,
or that belongs to a row with no detail, is ignored and stays in the state, and it opens the detail of
that row when the row comes later.

**The button** is the one control of its cell, as the box is in the column of boxes: it has the focus
and is the Tab stop while its cell is the active one. It is named `labels.showDetails(name)` while the
detail is closed and `labels.hideDetails(name)` while it is open, where `name` is the text of the row
header column (drawn or not), or the key when there is none. It says `aria-expanded`, and, while the
detail is open, `aria-controls` with the id of the detail row; the row of data says neither
(`aria-expanded` on a row would mean that it has child rows). A press on it opens or closes the
detail and chooses no row, whatever `selectOnRowClick` is, and does not call `onRowActivate`.

**The detail row** is the row after its master, drawn only while the detail is open. The cells before
the button's column (the box, the indents) are empty and have no band; one cell goes on from there to
the end of the row and holds the detail, on the band of the second level of a group. The content has
12px 16px 14px of room around it and may wrap. It sticks to what the frame shows: when the columns
are wider than the frame, and it is scrolled sideways, the content stays in sight, at the right of the
left zone and as wide as what is left between the zones. Its height is its content's. A `Table` in a
detail has the look of a Table that does not stick its heading.

The detail row is a place of the grid, with one cell, and it is in the order of the rows: <Kbd keys="down" />
from its master goes to it and <Kbd keys="down" /> from it goes to the next row, in the column the place
was in all the while. <Kbd keys="left" />, <Kbd keys="right" />, <Kbd keys="home" /> and

<Kbd keys="end" /> do nothing in it. Its content works as a cell that holds controls (see Keyboard):
<Kbd keys="enter" /> or <Kbd keys="f2" /> goes into the first control, <Kbd keys="tab" /> goes round
the controls, <Kbd keys="esc" /> or <Kbd keys="f2" /> comes back, and with no control
<Kbd keys="enter" />
does nothing. A control the detail draws is out of the Tab order, as the control of a custom cell
is, also one that it adds after a load. When a detail closes with the place on it, the place goes to
its master row, in the same column.

**A detail turns virtual scrolling off:** a detail has no fixed height, which the window of rows
counts on, so `scrolling="virtual"` with `renderDetail` scrolls as usual and warns once: it has
pages, at the default size, and `paging={false}` keeps one scroll of every row. **Pages** keep
a detail with its master and do not count it as a row. **Server mode** works on the page: the keys
are the keys of the rows the server sent.

## Reordering rows

`rowReorder` gives the grid a column of handles, 28px wide, after the column of boxes and before the
indent columns of a grouping, and lets a person move a row: by a drag of its handle, by a menu that
the handle opens, and by keys. **The grid moves nothing.** It tells `onRowReorder(fromKey, toKey,
position)` and your app changes `data`: the row `fromKey` goes `'before'` or `'after'` the row
`toKey`. Both rows are among the rows after the filter, in the order they are shown, so a move in a
filtered grid is counted among the rows the filter keeps, and one in a grid with pages is counted
over every page (in server mode, over the rows of the page: see below). `rowReorder` is for `true`
and no other value. Without `onRowReorder` the handles are drawn, a move calls nothing and says
nothing, and the grid warns once.

```tsx
const [orders, setOrders] = useState(initial);

<DataGrid
  data={orders}
  rowKey="id"
  columns={columns}
  caption="Orders"
  rowReorder
  onRowReorder={(from, to, position) =>
    setOrders((rows) => {
      const moved = rows.find((row) => row.id === from)!;
      const others = rows.filter((row) => row.id !== from);
      const at = others.findIndex((row) => row.id === to) + (position === 'after' ? 1 : 0);
      return [...others.slice(0, at), moved, ...others.slice(at)];
    })
  }
/>;
```

<Canvas of={GroupingStories.RowReorderDragging} />

**The handle** is a button of 20px by 24px, with the six dots of the Dialog's grip in the muted text
colour; it is the text colour under the pointer and the accent while its row is dragged. It is the one
control of its cell, as the box is in the column of boxes, so it has the focus and is the Tab stop
while its cell is the active one. It is named `labels.reorderRow(name)` ("Reorder DH-1024"), where
`name` is the text of the row header column (drawn or not), or the key when there is none, and it
says `aria-haspopup="menu"` and `aria-expanded` while its menu is open. The title of the column
has the hidden words `labels.reorderColumn` and is a place of the keyboard with no control.

**While the grid sorts or groups the handles do nothing**, since the order of the rows is then not the
rows' own: they are `aria-disabled` and dimmed to half, they start no drag and open no menu, and a
tooltip says why (`labels.reorderDisabled`), on hover and on focus; the handle stays focusable so that
a keyboard user finds the reason too, and the tooltip is its description. A filter does not turn them
off.

- **Drag the handle.** With a mouse, a pen or a finger (the handle has `touch-action: none` and is
  only for this). The row is dimmed to 35% while it is dragged (and its detail, while it is open), a chip
  with its name follows the pointer, and a line of 3px with a dot at its left end shows where it would
  go: across what the frame shows, at the boundary before the row under the pointer when the pointer is in
  its upper half and after it when it is in its lower half (after its detail while that is open). There
  is no line, and a drop does nothing, beside the row itself, over the heading or the footer, outside
  the rows and where the boundary is out of sight. The cursor is `grabbing` over the whole page until
  the pointer is let go. A grid with a `height` scrolls its rows when the pointer is within 40px of the
  frame's edge, and the page is not scrolled; a virtual grid reads the rows under the pointer from what
  it has drawn, and a row that left the window is no target, though the row that is dragged may.
  <Kbd keys="esc" />, `pointercancel`, a lost capture, the grid going and `rowReorder` turning off
  all end the drag and call nothing, and each takes off what the drag set: the dim, the chip, the
  line, the cursor, the scroll. `onRowReorder` is called once, at the drop, with the row under the
  line; the rows are drawn when the drag starts and when it ends (the source row only), and not for
  a move of the pointer.
- **The menu.** A press on the handle, <Kbd keys="enter" /> or <Kbd keys="space" /> on it opens the one
  menu of the grid, under the handle, with Move up, Move down, Move to top and Move to bottom
  (`labels.moveUp`, `moveDown`, `moveToTop`, `moveToBottom`). An item that would not move the row (up and
  top for the first row, down and bottom for the last, among the rows after the filter) is off. Choosing
  one makes the move and closes the menu, and the focus goes back to the handle of the row. The menu
  closes, for good, when `rowReorder` turns off, when the grid starts to sort or group, and when its row
  leaves the rows shown. <Kbd keys="space" /> is the button's: the browser presses it when the key is let
  go, and the key chooses no row.
- **Keys.** <Kbd keys="mod+shift+up" /> and <Kbd keys="mod+shift+down" /> on any cell of a row, the
  handle included, move it one place: up is before the row above and down is after the row below. At
  an edge the key does nothing, and it is cancelled all the same. While the grid sorts or groups it does
  nothing but say `labels.reorderDisabled`, once for a press.
- **What is said.** Every move, by the menu, the keys or a drop, is said at once (`labels.announceRowMoved`),
  with the place the row was asked for among the rows after the filter and how many there are, before
  your app has answered. A move that nothing keeps (no `onRowReorder`) says nothing.

**The focus follows the row.** The active place is the row's key, so it goes with the row when your app
moves it, and the focus stays on the cell it was on. When a move by the menu or the keys puts the row on
another page, the grid goes to that page once, at the first commit where the new `data` shows the rows in
the order that was asked for, scrolls the row into view the least it takes, and gives the place and the
focus back to it. That commit ends the request, whatever it shows: a `data` that you changed another way
is not this move's, and a move that your app never answers waits for no timer. So a controlled
`page` that your app updates a task later than its `onPageChange` does not get the follow step: the
next commit is one where the row is not shown yet, and it ends the request. Update `page` in the
same event. A drop is not followed: the pointer is on the row already.

**Pages and server mode.** In a grid with pages a move by the menu or the keys counts over every page,
and a drag counts over the page shown. In server mode `data` is the page, so every move is within it: the
keys and the menu stop at the edges of the page, and `onRowReorder` says the keys of rows of that page.

## Editing

`editing` turns on editing, and the data stays yours: **the grid never changes `data`**. What the user
types is held until it is saved, and `onSaving` is told; you change your data and pass the new rows.
There are five modes, which differ in what is an editor and what saves it (see the table below).

```tsx
<DataGrid
  data={orders}
  rowKey="id"
  columns={columns}
  editing={{ mode: 'row' }}
  onSaving={async (changes) => {
    // One change for each row: { type: 'update', key, data, row }
    await save(changes);
    setOrders(await load());
  }}
/>
```

`editing` is kept by value, so an object written in the JSX draws no row; `allowUpdating` is a function and
is compared by identity, so a function written inline in the JSX is a new one on each render of the parent
and draws every row again each time: keep it stable (`useCallback`, or a function outside the component).
The same goes for `allowDeleting`. A value that is no object, or a `mode` the grid does not have, is no
editing, with a warning.

| `editing` field   | Does                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------- |
| `mode`            | `'row'`: the editable cells of one row become editors at once, with ✓ and ✕                 |
| `mode`            | `'cell'`: one cell at a time is an editor, and each cell is saved as it is left             |
| `mode`            | `'batch'`: cells are edited as in `'cell'`, but each is only marked; the save bar sends all |
| `mode`            | `'form'`: Edit opens a form in the place of the row, with a field for every data column     |
| `mode`            | `'popup'`: Edit opens the same fields in a Dialog over the grid; the row stays as it is     |
| `allowUpdating`   | `true` (default), `false`, or a function `(row) => boolean`: which rows can be edited       |
| `allowAdding`     | `false` (default) or `true`: the toolbar's Add row button and `addRow()`; see Adding rows   |
| `newRowPosition`  | `'first'` (default) or `'last'`: where the new rows stand in the page shown                 |
| `allowDeleting`   | `false` (default), `true`, or a function `(row) => boolean`: which rows can be deleted      |
| `confirmDelete`   | `true` (default): Delete asks first in a dialog; `false` sends the delete at once           |
| `startEditAction` | `'click'` (default) or `'dblClick'`: what starts the edit of a cell in cell mode            |
| `popup`           | `{ size, movable, fullScreenOnPhone }` of the Dialog of popup mode; see Popup mode          |

**The five modes** (the keys of each are in the Keyboard table):

| Mode      | Starts with                                                                       | While editing                                                                                       | Saves with                                                      | Gives up with                                                        |
| --------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------- |
| `'row'`   | Edit; <Kbd keys="enter" /> or <Kbd keys="f2" /> on a cell of the row              | Every cell that can be edited is an editor; <Kbd keys="tab" /> goes through them, ✓ and ✕, then out | ✓; <Kbd keys="enter" /> in an editor                            | ✕; <Kbd keys="esc" /> (a list that is open takes the first one)      |
| `'cell'`  | A press (`startEditAction`), <Kbd keys="enter" />, <Kbd keys="f2" />, a character | One cell; <Kbd keys="tab" /> and <Kbd keys="shift+tab" /> go on to the next or previous             | Leaving the cell, <Kbd keys="enter" />: one `onSaving` for each | <Kbd keys="esc" /> gives the value up                                |
| `'batch'` | As `'cell'`                                                                       | As `'cell'`, but a commit only marks the cell                                                       | Save changes, `saveChanges()`: one `onSaving` for all of them   | Discard changes, `cancelChanges()`; <Kbd keys="esc" /> the cell only |
| `'form'`  | Edit; <Kbd keys="enter" /> or <Kbd keys="f2" /> on a cell of the row              | A form in the place of the row; <Kbd keys="tab" /> goes through the fields and the buttons          | Save; <Kbd keys="enter" /> in a field                           | Cancel; <Kbd keys="esc" />                                           |
| `'popup'` | As `'form'`                                                                       | A Dialog over the grid, with the same fields                                                        | As `'form'`                                                     | Cancel; <Kbd keys="esc" />; a press outside does not close it        |

In `'row'`, `'form'` and `'popup'` one row is edited at a time: starting another saves the one being
edited first, and stays on it when that save does not go through. In `'popup'` the Dialog covers the grid, so
the one way to start another row while it is open is `addRow()` of the handle, which saves the open one first.

A key held down starts and saves nothing, in every mode: only its first press counts, so <Kbd keys="enter" />
held on a cell or an editor does not open an edit and save it at once. A window that loses the focus (another
tab, Alt+Tab) settles nothing: the editor stays open, and no field is checked, until the user leaves it.

A row that cannot be edited now (marked for deletion in `'batch'`, a new row whose insert is being sent, a row whose
delete waits for its answer) has no editable cell: <Kbd keys="tab" /> in `'cell'` mode goes on to the next cell that
can be edited, and <Kbd keys="enter" />, <Kbd keys="f2" />, <Kbd keys="space" /> and a typed character on it are the
grid's own keys (they are not cancelled for an edit that does not open).

### Row mode

A column of buttons ends the row: **Edit** on each row that `allowUpdating` says yes to and that has a field to edit
(a cell it draws; in `'form'` and `'popup'` a field of the form), then **Delete** on each
row that `allowDeleting` says yes to (see Deleting rows). It is drawn while a button can stand in it (not with
`allowUpdating: false` and no `allowDeleting`), and a row of the grid is then 45px high (a `standard`
`lined` one; 4px more than without it, since a button is 28px; a `rowHeight` of yours is used as given). Edit
is there for a screen reader at all times and drawn when the row is hovered or holds the focus (always where
there is no hover). It is named `labels.edit(name)`, where the name is the text of the row header column, shown
or not, and the key when no column is the row header.

Press Edit, or <Kbd keys="enter" /> or <Kbd keys="f2" /> on a cell of the row, and every cell that can be edited
becomes an editor; the one pressed (the first, from Edit) has the focus. The others show their text. Only one
row is edited at a time: starting another saves the row being edited first, and stays on it if that save does
not go through. The row being edited stays in the rows: a search or a filter, yours or the user's, never takes it
away while it is edited. If your app takes the row out of `data` the edit ends as Cancel does, and nothing is
sent. A page change, a group that is closed or a virtual window scrolled away hide the editors and not the edit:
they come back with what was typed and do not take the focus again. Nothing of this is in the state of the grid
(`getState()`, `onStateChange`).

<Kbd keys="tab" /> goes through the editors, then ✓ (`labels.save(name)`) and ✕
(`labels.cancelEdit(name)`), then out of the grid; the row stays being edited. <Kbd keys="enter" />
in an editor saves, and <Kbd keys="esc" /> gives the edit up (the first <Kbd keys="esc" /> closes
the listbox or the calendar of an editor that has one open). When the editors go, the focus goes to
the cell of the one that had it, never to the page. Turning `editing` off or changing its `mode`
does the same for a focus that was in an editor, the form, the popup, the confirm or the save bar:
it goes to the cell of the place.

### Cell mode

`mode: 'cell'` edits one cell at a time. There is no Edit button, so the column of buttons is drawn only with
`allowDeleting` (Delete alone, shown on the row that is hovered or holds the focus); without it the rows are
as high as the rows of a grid with no editing. The one cell that is edited is an editor with the frame of
the focus and no lines at its sides (the lines are the sign of a row).

A cell is started by a press (`startEditAction: 'click'`, the default; `'dblClick'`: the first press only
places the focus and the double press starts the edit), by <Kbd keys="enter" /> or <Kbd keys="f2" /> (the value
is kept and the caret is at its end), or by typing a character: an editor with a text field (a string, a
number, a date, a lookup that is searched) opens with that character as its text, typed once; on a Select or
a Checkbox a character does nothing. A press, plain or double, on a cell that can be edited chooses no row
(even with `selectOnRowClick`) and activates none: it belongs to the edit, and `onRowActivate` is for the rows
and the cells that cannot be edited. To choose a row the user presses a cell that cannot be edited, or uses
the box of `selectionMode="multiple"`, or <Kbd keys="space" /> on a cell that is not a boolean. A press on a
boolean cell, and

<Kbd keys="space" /> on it, flip it and save it, with no editor opened and no row chosen (with
`startEditAction: 'dblClick'` the double press flips it, once; <Kbd keys="enter" /> and
<Kbd keys="f2" /> open its Checkbox); on any other cell <Kbd keys="space" /> chooses the row as it
did.

A cell is saved when it is left: the focus goes anywhere else, <Kbd keys="enter" /> (the editor closes and the
focus stays on the cell), or <Kbd keys="tab" /> and <Kbd keys="shift+tab" />, which save it and open the next
or the previous cell that can be edited, across the rows. At the last editable cell <Kbd keys="tab" /> saves it,
leaves the focus on the cell and goes on out of the grid; <Kbd keys="shift+tab" /> does the same before the
first. <Kbd keys="esc" /> gives the value up and the focus stays on the cell (the first <Kbd keys="esc" />
closes a popup of the editor, and the tooltip of an error). Nothing is sent when the value is the one the cell
shows. A value that fails its rules is not sent: the editor stays open with the error look.

**Each save is one `onSaving`**, with one `update` that holds only the fields of that cell. While a
Promise is pending the grid can be edited on: the cell shows its new value, and the next saves wait
and are sent one after the other, in order. The `row` of each `update` is the row as the grid shows
it when that save is sent: the saved row with the saves sent before it, so `{ ...row, ...data }` is
the whole new row and never reverts an earlier cell of the same row. When a save is refused, the
value goes back into its cell with the error look and the words of the error (the field the error
names, else the error's `message`, else `labels.saveFailed`) and the alert shows too; <Kbd keys="enter" />
there sends it again and <Kbd keys="esc" /> drops it; the saves that wait go on, and the alert stays while they
do (only a save the user starts, or settling that cell, takes it away). If another cell is being edited at
that moment, the refused value is not lost: it stays over its row as a failed change, drawn like a cell a
refused batch save named (the error frame, the icon, its words in the tooltip and in hidden text), and the
alert shows. A press on that cell, or <Kbd keys="enter" /> on it, opens its editor with the refused value, and
pressing <Kbd keys="esc" /> there drops it, so the cell shows the saved value again. A Promise that never
settles keeps the saves behind it waiting: nothing else is sent until it does, or until `editing` is turned
off. Turning `editing` off or changing its mode drops what waits.

### Batch mode

`mode: 'batch'` edits cells as `'cell'` does (a press, <Kbd keys="enter" />, <Kbd keys="f2" />, a character, <Kbd keys="tab" />
and <Kbd keys="shift+tab" />, <Kbd keys="space" /> and a press on a boolean), but nothing is sent when a cell is left: the
change is kept and marked, and one `onSaving` sends all of them when the user asks. <Kbd keys="esc" /> gives up the cell
being edited and nothing else. The column of buttons is drawn only with `allowDeleting`, as in cell mode.

- **A changed cell** (a value that is not the saved one) has a wash of the accent at 12%, a dashed frame inside it,
  and the hidden words `labels.changedCell` after its value. A value typed back to the saved one leaves no mark.
- **Delete** marks the row, with no question: its cells have the red wash, muted text and a line through them (a
  Badge too), its first cell says `labels.deletedRow` for a screen reader, and `labels.announceRowMarkedDeleted`
  is said. The cell of buttons holds **Undo** (`labels.undoDelete(name)`), always drawn, which gives the row back
  with the edits it had. A row marked for deletion cannot be edited. Delete on a new row gives it up.
- **The save bar** is the first thing in the main part, joined to the top of the frame, while at least one row has
  a change: the number of **rows** with a change (`labels.unsavedChanges(n)`; a new row and a row marked for
  deletion each count one, a row of two changed cells one), **Discard changes** and **Save changes**, which loads
  while the save is pending. The first change is said once. The Add row button is `secondary` while the bar shows.
  The bar is a stop of Tab between the toolbar and the grid, and when it goes with the focus in it the focus goes
  to the place of the grid.
- **Saving** (Save changes, or `ref.current.saveChanges()`) first commits the cell being edited, then checks every
  field of every changed row that can be edited (a new row: every field it draws) and, if one fails, announces the
  count (`labels.announceErrors`), opens the editor of the first and sends nothing. Otherwise **one** `onSaving`
  gets every change, one for each row: `insert`, `update` (the changed fields and the saved `row`) and `remove`.
  When it answers, the changes sent are cleared; the ones made while it was pending stay, over the row as it is
  saved now (a value typed back to the saved one while the save is pending is one of them: the server will hold
  what was sent). When it is refused (a reject or a throw) every change stays and the alert shows. The cells the
  `fieldErrors` name in the rows the grid draws are marked, with the red frame, the icon and the words (hidden in
  the cell for a screen reader, and in a tooltip that opens while the cell has the focus or the pointer, as an
  editor's does, and <Kbd keys="esc" /> closes); the mark goes when the cell is edited again and at the next
  save. The words of a field no row draws, or of a row that is not there, are in the alert. While the save is
  pending, Undo and Delete of a row whose change is being sent do nothing (`aria-disabled`, dimmed like any
  disabled button, and the focus stays where it is): the app is about to answer for that row.
- **Totals** read the values the cells show, and leave a row marked for deletion out.

`ref.current.saveChanges()` and `cancelChanges()` are the handle of every mode: in `'row'` mode they save and give up
the row being edited, in `'form'` and `'popup'` mode the open form or Dialog (a save runs every rule, as Save does), in
`'cell'` mode they commit the cell being edited and send the new rows and the refused values that are held over their
rows (a refusal is a change that is not saved: each is sent again, its mark gone, and `saveChanges()` resolves `false`
if one is refused again), or drop them. A new row that fails its rules is not sent and makes it `false`, whether or not
a field of it can take the focus (a computed column with a rule has none; <Kbd keys="tab" /> still leaves the grid).
`saveChanges()` resolves `false` when the grid stops waiting for the answer: it unmounts, `editing` is turned off or its
mode changes (the answer, when it comes, is ignored).

### Form mode

`mode: 'form'` opens a form in the place of the row. Edit (always drawn in this mode, with Delete), <Kbd keys="enter" /> or

<Kbd keys="f2" /> on a cell of the row opens it, one at a time: the form that is open is saved
first, and stays open when its fields fail their rules. The form is one row with one cell across
every column, and in the cell a floating glass card: a title (`labels.editRowTitle(name)`,
`labels.newRowTitle` for a new row), the line `labels.requiredHint` when a field is required, the
fields and the buttons Cancel (`labels.cancel`) and Save (`labels.saveButton`, which loads while the
save is pending).

The form stands in the place of its row, and the row stays in the selection: "select all" on the page (and mod+A)
chooses it by its key, the box of the title counts it, and it is the anchor of a range by Shift. The form of a new row
is not chosen, as no new row is.

- **The fields** are every data column in the order of the grid's columns, the hidden ones and the ones the grouping
  takes out too, but a column that says `form: { visible: false }`. Each is a `Field` with its caption above it, a
  star and `required` for a column with a `required` rule, and its error under it. The card is one column of fields
  and two from 480px of its own width; a `multiline` string column (a Textarea, which only the form and the popup
  edit) and a column with `form: { span: 2 }` span both. A column that cannot be edited is a label over its text,
  written as the cell writes it. The editors are the ones of Editing, always `md`.
- **Keys.** The field of the cell that <Kbd keys="enter" /> or <Kbd keys="f2" /> was pressed on has the focus when the form opens, when that column can be edited; else the first field that can be (Edit and a new row start there). <Kbd keys="tab" /> goes through the fields
  and the buttons in order; <Kbd keys="enter" /> in a field submits the form, which saves (not in a Textarea, nor
  from a list that is open); <Kbd keys="esc" /> gives it up, a list or a calendar that is open taking the first one. No
  other key of the grid runs inside the form. The form row is one place of the keyboard, as a detail row is: the
  arrows land on its cell, and <Kbd keys="enter" /> there goes into the form. When the form goes the focus is in the
  grid, never on the page.
- **Saving** checks every field of the form (the fields are checked when the focus leaves them too); a field that
  fails is not sent, the first has the focus, and `labels.announceErrors` is said. One `onSaving` gets one `update`
  with the changed fields (or one `insert` for a new row, whose form stands first or last as the new rows do). A refusal keeps the
  form and shows the alert; what `fieldErrors` names for a field goes under that field.
- **With a detail,** the row's detail is not drawn while its form is open and comes back with it (its state is kept).
- **Virtual:** the form row is the one row that is measured; before it is, it counts as eight rows.

### Popup mode

`mode: 'popup'` edits a row in a Dialog over the grid. Edit (always drawn in this mode, with Delete),

<Kbd keys="enter" /> or <Kbd keys="f2" /> on a cell of the row, and `addRow()` open it. It is one
Dialog for the grid, drawn after the table, and **the row stays in the table as it is**: no editor
opens in it and its buttons are the same as before. The fields, the title
(`labels.editRowTitle(name)`, `labels.newRowTitle`), the line `labels.requiredHint` (the Dialog's
description, when a field is required), the checks, `onSaving` and the errors are those of the form
(see Form mode); the buttons are Cancel (`labels.cancel`) and Save (`labels.saveButton`, which loads
while the save is pending), at the end of the Dialog's footer.

`editing.popup` sets the Dialog:

| `popup` field       | Does                                                                                                              |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `size`              | `'sm'` (360px), `'md'` (480px) or `'lg'` (640px, default): the width of the panel                                 |
| `movable`           | `false` (default) or `true`: the Dialog is dragged by its header on screens 640px and wider                       |
| `fullScreenOnPhone` | `true` (default) or `false`: below 640px the Dialog fills the screen, with Cancel and Save sharing the bottom row |

- **Not movable by default.** The approved look has a header with no grip, and a field that is typed in is no place
  for a Dialog that moves under a stray drag. `movable: true` is the library's movable Dialog (the grip, the keys of
  the Dialog stay as they are).
- **Full screen on phones.** Below 640px the panel is the window, with no margin and no corners, and the fields are
  one column (two from 480px of the Dialog's own width). `fullScreenOnPhone: false` keeps the centred panel on a phone.
- **Keys.** The field of the cell that <Kbd keys="enter" /> or <Kbd keys="f2" /> was pressed on has the focus when
  it opens, when that column can be edited; else the first field that can be (Edit and a new row start there). **On a
  phone, when the Dialog opens full screen, the focus starts on the title instead**, so the keyboard of the phone does
  not cover half the form; <Kbd keys="tab" /> then reaches the first field. <Kbd keys="tab" /> stays inside the Dialog;
  <Kbd keys="enter" /> in a field submits it, which saves (not in a Textarea, nor from a list that
  is open);
  <Kbd keys="esc" /> gives it up, a list or a calendar that is open taking the first one. **A press
  outside the panel does not close it** (`closeOnOutsideClick` is off), so a stray press loses
  nothing.
- **Saving** is the form's: every field is checked (the first that fails has the focus, under its error), and one
  `onSaving` gets one `update`, or one `insert` for a new row. A pending save keeps the Dialog open, with Save
  loading; it closes when the Promise resolves. A refusal keeps it open with the alert, and what `fieldErrors` names
  goes under that field. Cancel and <Kbd keys="esc" /> stay live while the save is pending: they close the Dialog and
  the grid stops waiting, so the answer, when it comes, is ignored (nothing is shown, nothing is kept).
- **The focus** goes back to what had it when the Dialog opened (the cell, or Edit). A new row that was saved has no
  cell to go back to, and then the focus goes to the place of the grid: never to the page.
- **It goes for good** when its row is no longer among the rows shown, when `editing` turns off or changes its mode,
  and when the grid unmounts; nothing is sent. A new row is a row of the grid, drawn as in the other modes
  while its Dialog is open (a virtual grid does not scroll to it), and dropped by Cancel.

### What is edited

`allowEditing` of a column (`true` when left out, or a function `(row) => boolean`) says which cells. A cell is
shown as text, in the row being edited too, when its column says no, when it computes its value and has no
`setValue`, when it is a `datetime` with no `editor`, and when it is a `multiline` string column in the modes that edit
in the cell (the Textarea is the one of the form and of the popup). The grid warns once for a computed column that asks to be
edited (`allowEditing`) and has no `setValue`, and for a `multiline` that is not on a string column.

`allowEditing` and `allowUpdating` are asked of one row, the row as the grid shows it: the saved values with the
changes held over them (the ones of a batch, a pending save). The cells are drawn by it, a key or a press starts
them by it, and a save checks the cells by it, so a function that reads a field the user changed (`(row) =>
row.status !== 'closed'`) draws the editors and checks the fields of the same row. The function is called once
for each cell when a row is drawn. A function of yours that throws (`allowUpdating`, `allowDeleting` or a column's
`allowEditing`) counts as `false`, with one warning, and the grid goes on.

The editor of a column is chosen by its type, and is named by the column's caption (`sm` in a `compact` grid,
`md` elsewhere):

| Column          | Editor                                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------- |
| `string`        | `Input`                                                                                                       |
| `number`        | `NumberInput`, in the grid's `locale` and by the column's Intl `format` options                               |
| `date`          | `DatePicker`; a `Date` in the row is saved as a `Date` at the UTC midnight of the day, a string as an ISO day |
| `boolean`       | `Checkbox`, in the middle of the cell                                                                         |
| with a `lookup` | `Select` up to 20 items, `Combobox` above; `lookup.searchable` is `true` or `false` to force one              |
| `datetime`      | none: give the column an `editor`                                                                             |

A column's own `editor(ctx)` replaces the default. It is given `{ row, value, setValue, commit,
cancel, invalid, errorId, saving, mode, size, autoFocus, label }`; `setValue` takes the value as the
row holds it. The element it returns keeps its own handlers. `saving` is `true` while the save of
the row waits for its answer: make the control read-only then, as the grid's own editors are.
`commit()` checks the field as leaving it does, in every mode (a refusal sets `invalid` and
`errorId`, the id of the words that say why: hidden text of the cell, or the message under the field
of the form or the popup); in `'cell'` mode a value that passes is committed and the editor goes, in
`'batch'` it is held as a change. Name the control with `label` in a cell only: the form and the
popup have a `<label>` of their own for it. An `editor` that throws is caught: the grid warns once
and draws the editor of the column's type in its place. A computed column is edited through its
`setValue(row, value)`, which turns the value into the fields of the row (a `setValue` that throws
warns once and sets nothing). A change is found field by field, and a value that is an object or an
array is compared with the saved one by identity: a `setValue` or an editor that builds an equal copy
counts as a change, so give back the saved object when nothing was changed:

```tsx
dataGridColumn<Order>()({
  id: 'total',
  dataType: 'number',
  value: (order) => order.qty * order.price,
  setValue: (order, total) => ({ ...order, price: (total ?? 0) / (order.qty ?? 1) }),
});
```

### `onSaving`

Saving calls `onSaving` once with one `update` for the row: `data` holds only the fields that changed (a value
typed back to what it was is no change), and `row` is the saved row. A row with no change saves nothing, and
the edit ends. What `onSaving` returns tells how it went:

- Anything but a Promise is a success at once: the edit ends and `labels.announceSaved` is said.
- A Promise is waited for: the table is `aria-busy`, ✓ is `loading` and the editors cannot change (a field is
  read-only, and a Select or a Checkbox ignores its change; none is `disabled`, so the focus stays). When it
  resolves the edit ends and `labels.announceSaved` is said; you change `data`. When it rejects, or when
  `onSaving` throws (which warns once), the edit stays with what was typed, and can be saved again.
- Without `onSaving` a save drops the change and ends the edit, and the grid warns once.

A request ends: when the edit is given up (not in `cell` mode, where giving up a cell leaves the saves sent or
waiting alone), `editing` turns off or its mode changes, or the grid unmounts, the grid stops waiting and ignores
the answer. The row keeps the place when your new `data` moves it (sorted,
grouped or on another page); it falls to the row at the same index when the row is gone from the list.

### Validation

A column's `validationRules` is a list of rules, run in order; the first that fails gives the message and the
rest do not run. Every rule but `required` passes a blank value.

| Rule           | Fails when                                                                            |
| -------------- | ------------------------------------------------------------------------------------- |
| `required`     | the value is blank (empty text, no number, no date)                                   |
| `range`        | a number, or an ISO day, is outside `min` and `max` (either may be left out)          |
| `stringLength` | the text is shorter than `min` or longer than `max` characters                        |
| `pattern`      | the text does not match the `RegExp`                                                  |
| `email`        | the text is not one `@` with a dot after it (loose on purpose)                        |
| `custom`       | `validate(value, row)` returns a text (the message) or `false` (the rule's `message`) |

A rule's own `message` wins; otherwise the words are `labels.validation`, a record merged one level deep
(`required(caption)`, `range(caption, min, max)`, `stringLength`, `pattern`, `email`). A `custom` rule that
returns `false` and has no `message` says the words of `labels.validation.pattern`. A rule that throws passes,
with one warning.

A field is checked when its editor lets go of the focus (to another cell of the page; a popup of the editor
is part of it), or when the editor calls `ctx.commit()`; and **every cell of the row that can be edited** is
checked when the row is saved, the ones nobody touched too (a row that changed nothing is not saved, so it is
not checked). A save with a field that fails sends nothing, puts the focus on the first of them in the order of
the cells, and says `labels.announceErrors(n)`, where `n` is the number of fields. A field that was fixed loses
its mark at its next commit, not while it is typed in; the mark of a field whose column has no rule stays
until the row is saved again.

A refused cell has a frame of 2px in the danger colour (an outline in forced colours) and an icon at the end of
its editor. The message is hidden text in the cell that the editor is described by (`aria-invalid`,
`aria-describedby`; a custom `editor` is given `invalid` and `errorId`), and the same words open in a tooltip
below the cell while it holds the focus or the pointer.

### Errors when saving

When the Promise `onSaving` returned rejects (or `onSaving` throws), the edit stays and one error alert shows
between the toolbar and the table, with a button that takes it away (named `labels.dismissError`). Its words are the `message` of what was
thrown when that is a text, else `labels.saveFailed`; the alert is its own announcement. It goes when it is
dismissed (the focus goes to the place of the grid), at the next save the user starts, when the edit is given
up, and when `editing` turns off. In `cell` mode a save that goes on by itself from the queue does not take it
away, and only <Kbd keys="esc" /> in the refused cell gives it up: the <Kbd keys="esc" /> of any other cell leaves
it alone. The focus stays where it was.

Reject with a `DataGridSaveError` to mark the fields the server refused:

```tsx
onSaving={async (changes) => {
  const answer = await post(changes);
  if (!answer.ok) {
    throw {
      message: 'Some fields are wrong.',
      fieldErrors: [{ key: 'DH-1028', field: 'customer', message: 'Already taken' }],
    };
  }
}}
```

A `field` that names a column the row draws (by id, else by `field`) marks that cell with the message; one the
row does not draw (a hidden column, another row) adds its message to the alert's words.

### Deleting rows

`allowDeleting` puts **Delete** (`labels.delete(name)`) after Edit, 2px apart, shown as Edit is, on rows that are
not being edited. With `confirmDelete` (the default) it opens one dialog for the grid, with `labels.deleteTitle`,
`labels.deleteDescription(name)`, Cancel (`labels.cancel`, focused first) and Delete
(`labels.deleteConfirm`); <Kbd keys="esc" /> and Cancel close it. Delete in the dialog closes it and calls
`onSaving([{ type: 'remove', key, row }])`; the dialog does not wait for the answer, the table is `aria-busy`
while a Promise is pending, a reject shows the alert, and `labels.announceRowDeleted` is said when it has gone
through. A delete that waits does not lock the edit of another row: its editors stay editable and ✓ or Save saves it,
while a second delete waits for the first. The row whose delete is pending cannot be edited (in every mode but
`'batch'`, which sends no delete of its own): a press, <Kbd keys="enter" />, <Kbd keys="f2" /> and a typed character
on its cells and its Edit button do nothing, and its Edit and Delete buttons are `aria-disabled` and dimmed until the
answer. Without `confirmDelete` the press sends at once. The focus goes to the cell of the row's buttons when
the dialog closes or the press sends, and to the row now at its place when your `data` drops the row. A dialog
whose row leaves the rows shown, or whose feature turns off, closes for good.

### Adding rows

`allowAdding` puts the **Add row** button (`labels.addRow`, a primary `md` button with a plus) last in the toolbar, and
enables `ref.current.addRow()`, which does the same and does nothing without `allowAdding`. A new row is a row of
the grid that is not in `data`: its key is `flg-new-1`, `flg-new-2`, … (a counter of the grid that never gives a
number twice; a key of `data` that equals one is skipped, with a warning), and it is edited whatever
`allowUpdating` says. `labels.announceRowAdded` is said.

- **Where it stands.** At the top of the page shown (`newRowPosition: 'first'`) or at its bottom (`'last'`), outside
  every group, whatever the sort; the search and the filter keep it. It stands on every page and is **not
  counted**: the pager, the "rows found" sentence and "select all" read the rows of `data`
  only. It has no box, no handle and no detail button (their cells are empty and still places of the keyboard),
  and <Kbd keys="space" />, a press, a double press and <Kbd keys="enter" /> never choose, move or activate it.
- **Its fields.** `initNewRow()` gives the fields it starts with; it is read each time a row is added (never kept from
  the first render), a throw is caught and warned once, and the row then starts empty. The cells that no editor
  holds say "+ (new)" (`labels.newRow`) in the row header's cell, and a dash where a read-only cell has nothing to
  show. A new row holds only the fields `initNewRow()` gave and the ones typed, though its type is `TRow`: a column
  that reads a field of the row (a `value`, a `format` or a `cell`, `rowClassName`, a custom total) should find it
  in `initNewRow()`. When such a function throws on a new row the grid catches it, warns once and leaves what it
  drew blank; the same functions of the saved rows are never caught. A column's `allowEditing` is given a new row
  too, and a throw counts as `false`, with one warning. `allowUpdating`, `allowDeleting`, `sortValue`,
  `rowHasDetail`, `renderDetail` and `onRowActivate` are never given a new row: it is always edited, Delete gives it
  up, it is not sorted, has no detail and is not activated.
  The check of the rules never throws: a `value` that throws while a row is validated is taken as a blank (so
  `required` fails and the other rules pass), with one warning.
- **Row mode.** The row opens in edit mode with the focus in its first editor. ✓ and <Kbd keys="enter" /> call
  `onSaving([{ type: 'insert', key, data }])` with the fields `initNewRow()` gave and the ones that were set, after
  every cell the row draws has been checked; ✕ and <Kbd keys="esc" /> drop the row and send nothing. Adding while a row
  is edited saves that row first, and adds none if that save does not go through (one row at a time). A grid that
  only adds (`allowUpdating: false`) still has the column of buttons, for ✓ and ✕.
- **Cell mode.** The first cell that can be edited opens. The commits of its cells only fill the row; it is sent as
  one `insert` when the place of the keyboard leaves the row, when another cell is started, when another row is
  added, or when <Kbd keys="tab" /> leaves the grid after the last cell, once the fields it draws have been
  checked (a row that fails keeps the place, with the editor of the first failing cell open and marked). A row that
  was given nothing is dropped, never sent. A refused insert keeps the row, with the alert, and is sent again the
  next time the place leaves it. With `allowDeleting`, Delete gives a new row up with no question, but not while
  its insert is being sent (or queued): the button is `aria-disabled` and dimmed until the answer, as in `'batch'`
  mode.

## Loading and empty

`loading` says that the data is on its way. It is the same on the server and in the browser, and
what it shows depends on whether there is anything to show:

- **Nothing yet** (`loading` and no row): a page of skeleton rows stands where the rows will be: as
  many as a page holds (`paging.pageSize`, or the page size in use), and at most 20; 20 when the
  grid has no pages. They are as tall as rows of data, and are ruled or striped as the rows of the
  grid are, since they are rows of a Table. Each cell of a column holds a `Skeleton` that pulses, as
  wide as 40% to 80% of the cell, fixed by the place of the column, so no two renders differ and the
  blocks do not line up. The column of boxes of `selectionMode="multiple"` has none. The rows are
  hidden from assistive technology, are not rows of data (no `aria-selected`) and cannot have the
  keyboard; the heading is the one stop of Tab, and there is no bar of pages.
- **Rows already** (`loading` and rows, which is a load that replaces what is shown, a new page in
  server mode, say): the rows stay, and a layer goes over them, from the bottom of the heading to
  the bottom of the frame, with a `Spinner` in the middle of what is seen. It is a wash of the
  surface, `color-mix(in srgb, var(--flg-glass-tint-solid) 55%, transparent)`, and in forced colours
  it is transparent and the spinner shows. The layer is only to look at and takes no pointer: the
  wheel, the scrollbar and a press reach the frame and the cells under it, and the heading, the
  caption and the bar of the pages stay in use. It is in the main part of the grid, not in the
  frame, so it does not scroll with the rows. The keyboard still works, so a load that is slow does
  not trap anyone; it is for the app to ignore what it does not want while it loads. The grid
  measures its heading to place the layer, only while the layer is there.
- **Either way** the table is `aria-busy="true"`, and the grid says `labels.loading` once, when the
  load has lasted a second, through its live region: `aria-busy` already says that it is loading,
  and a load that is over sooner is not worth a sentence. A `loading` that goes off and on again
  within that second is one load, and the next load says it again. Nothing is said to the region
  before then and nothing is cleared from it, so a sort that you announce in the same press is
  heard.

An empty grid (no row and not `loading`) draws one row with one cell across every column, and in it
`labels.noData` ("No data"): centred, wrapping, in the small semibold text, with padding of 26px at
the top and the bottom. It is not a row of data and nothing in it takes the keyboard, so the active
cell is a title, and there is no bar of pages. The words are as wide as what the frame shows and
stay at its left edge when the columns are wider than the frame and it has been scrolled sideways,
so the grid measures its frame while they are drawn.

## State

The sort, the filter, the page, the chosen keys, the layout of the columns, the grouping, the open
groups and the open details are each a controlled or an uncontrolled value, as every field of the
library: `sort`,
`defaultSort` and `onSortChange`; `grouping`, `defaultGrouping` and `onGroupingChange`, and
`expandedGroups`, `defaultExpandedGroups` and `onExpandedGroupsChange` (see Grouping);
`expandedRows`, `defaultExpandedRows` and `onExpandedRowsChange` (see Master-detail);
`filter`, `defaultFilter` and `onFilterChange` (see Filtering); `page`, `defaultPage` and
`onPageChange`; `selectedKeys`, `defaultSelectedKeys` and `onSelectedKeysChange`; `columnLayout`,
`defaultColumnLayout` and `onColumnLayoutChange` (see Column layout). A controlled value that you do
not take stays as it was, and the callback still hears the press.

`onStateChange(state, changed)` is called after `onSortChange`, `onFilterChange`, `onPageChange`,
`onSelectedKeysChange`, `onColumnLayoutChange`, `onGroupingChange`, `onExpandedGroupsChange` or
`onExpandedRowsChange` (then `changed` is `'expandedRows'`) with the whole state,
`{ sort, filter, page, selectedKeys, columnLayout, grouping, expandedGroups, expandedRows }`, and
the name of the part that changed, so that
one function can save the state of the grid. The state is the one the grid shows, as `getState()`
returns it, with the part the press asks for in its place: a page that is past the end of the data
is sent as the page that is drawn, so what you save is never a page that is not there. It is called
from what a person does, never from a render: a controlled value that you change from outside does
not call it. The one exception is the page that server mode asks for (see Server mode). The state
holds only what JSON can carry, so it can go to `localStorage` or to a server and come back as the
eight `default*` props: `defaultSort`, `defaultFilter`, `defaultPage`, `defaultSelectedKeys`,
`defaultColumnLayout`, `defaultGrouping`, `defaultExpandedGroups` and `defaultExpandedRows`. The
recipe in "Saving the state" below does it for five of them.

`ref.current.getState()` returns the state the grid shows as its last commit left it, which is from
its first commit on: what you hold, but with the page as drawn.

A saved state may come back in a shape its type does not allow, and so may a prop from JavaScript:
the grid never throws on one. A `sort` or `selectedKeys` that is not an array is empty, and an item
of it that is not a sort item or a key is left out; a `page` that is not an object of a number
`index` and `size` is the first page, or the size of `paging`. `data` and `columns` that are not
arrays are empty, a `paging` that is neither `false` nor an object is the default paging, and a
`paging.pageSizes` that is not an array offers the default sizes, and a `filter` that is not an
object is the empty filter (the parts of one that are not of their kind are left out). Each such
prop warns once in
development, without its value. What a state may hold for good reasons is still taken without a
word: a column that is gone, a direction or a key that means nothing, a page out of range.

### Saving the state

The grid has no `stateStoring` option: it does not know where an app keeps things. The state goes out
through `onStateChange` and comes back through the `default*` props, and the recipe below is the
whole of it. It is the component that the unit tests run, line for line.

```tsx
'use client';
import { useEffect, useState } from 'react';
import { DataGrid, type DataGridState } from 'h2d-glass-ui';
import { columns, type Order } from './columns';

const KEY = 'orders-grid-v1';

function OrdersGrid({ data }: { data: Order[] }) {
  const [saved, setSaved] = useState<Partial<DataGridState> | null>(null);
  useEffect(() => {
    try {
      setSaved(JSON.parse(localStorage.getItem(KEY) ?? 'null'));
    } catch {
      // Private mode or text that is no JSON: the default state stays.
    }
  }, []);
  return (
    <DataGrid
      key={saved ? 'saved' : 'default'}
      data={data}
      rowKey="id"
      columns={columns}
      caption="Orders"
      defaultSort={saved?.sort}
      defaultFilter={saved?.filter}
      defaultGrouping={saved?.grouping}
      defaultColumnLayout={saved?.columnLayout}
      defaultPage={saved?.page}
      onStateChange={({ sort, filter, grouping, columnLayout, page }) => {
        try {
          localStorage.setItem(KEY, JSON.stringify({ sort, filter, grouping, columnLayout, page }));
        } catch {
          // Private mode or a full storage: the state is not kept, the grid goes on.
        }
      }}
    />
  );
}
```

<Canvas of={Stories.SavedState} />

**The server's HTML is the default state.** The recipe reads `localStorage` in an effect, never
while it renders, so the server and the first render in the browser draw the same grid. After the
mount it sets the stored state, and the `key` changes from `default` to `saved`: the grid mounts
once more with the stored state as its starting values. So the recipe costs one more mount: the grid
draws the default state first, and the focus and the scroll of that first mount are not kept.

**What it saves.** The sort, the filter, the grouping, the layout of the columns and the page: what
a person arranges to read the data in their way. It leaves out `selectedKeys`, `expandedRows` and
`expandedGroups`, which belong to one sitting: a selection or an open detail that comes back
tomorrow is a surprise. To save them as well, add them to the object that `onStateChange` stores,
and give them back as `defaultSelectedKeys`, `defaultExpandedRows` and `defaultExpandedGroups`: three
more props and three more fields.

**A state meets the columns it finds.** The columns can change between two visits, and the grid
takes the stored state without a word:

- a column id that is gone is dropped from the layout (from the order and from the hidden columns, and
  it is not in the state the grid gives back), and a column that is new is appended to the order;
- a sort or grouping item of a field the grid does not have is ignored, and stays in the state;
- a filter condition of a column the grid does not have stays, and filters nothing;
- a page past the end is the last page.

When the columns change a lot, change the suffix of the key (`orders-grid-v2`): the old state is
never read again.

**A state of the wrong shape is the default.** A `sort` that is not an array, or a `page` that is
not an object, comes from a storage that someone edited or from another version of the recipe. The
grid never throws on it: that part is its default, and the prop warns once in development, in the
words of `defaultSort is not an array of sort items`, without the value. Text that is no JSON is
the default too, and warns nothing: the recipe catches it.

**Private mode and a full storage.** `localStorage` can throw, on a read and on a write. Both calls
are in a `try`, so the grid goes on without keeping its state.

**The edit state is not in it.** Unsaved changes, the row or the cell being edited, a save that is
being sent and its errors are never in `DataGridState`, in `getState()` or in `onStateChange`: an
edit calls none of them. Bringing them back after a reload would write old edits over data that
has changed since, would keep rows that are not complete in the browser's storage, and would go
around `onSaving`, the one path that a change takes to your data.

## Keyboard

The grid follows the data grid pattern of the WAI-ARIA Authoring Practices: it is **one stop of
Tab**, and the arrow keys move inside it. Exactly one cell, or one column title, has `tabindex="0"`:
the active cell. A Tab from before the grid lands on it, and the next Tab leaves the grid for what
follows (the filter panel and the pager, if there are any). Everything else in the table is
`tabindex="-1"`: the other cells and titles, the sort buttons, and every link, button or field that
a `cell` puts in a cell. The grid sets that on the controls of your cells after each render, and on
a control that a cell adds by its own render (a link that comes after a fetch) or makes one by an
attribute (a button it enables, a link that gets its `href`, a roving `tabindex` it moves), which it
watches the rows for while a column has a `cell`. The heading is always watched, since the controls
of its filter row render on their own (a date cell makes its picker anew on Esc). It gives each its
own `tabindex` back, as it was, when the grid goes; a `tabindex` your cell writes later is yours, and a negative one stays. A popup
in a cell (a `[popover]` or a `dialog`) is a place of its own: its controls keep their `tabindex`,
so Tab goes through them while it is open.

The active cell is a row and a column, said by the row's key and the column's id, so a sort, a page
or a window that moves the row does not lose the place. At first it is the first cell of the first
row, or the first title when there is no row. A press on a cell, or on a control in it, makes that
cell the active one. When the row of the active cell leaves `data`, the place moves to the row now
at the same index (the one before it when it was the last, the title when none is left), and the
focus follows it when it was in the grid, so it never falls to the page.

After a press in the grid the focus is on the cell that was pressed, on its box in the column of
boxes, and on the title after a press on its sort button (which still sorts), so the arrow keys go
on from there and the next Tab leaves the grid, as after a sort by the keyboard. A press with Shift
or a modifier is no different. Only a press on a control that a `cell` holds leaves the focus on the
control (see Cells that hold controls).

### Cells that hold controls

A `cell` may put a link, a button or a field in a cell. The cell is what has the focus and is the
Tab stop; <Kbd keys="enter" /> or <Kbd keys="f2" /> on it goes into **widget mode**: the first
control has the focus, <Kbd keys="tab" /> and <Kbd keys="shift+tab" /> go round the controls of the
cell and do not leave it, and <Kbd keys="esc" /> or <Kbd keys="f2" /> come back to the cell. In
widget mode every other key is the control's own: an arrow moves the caret of a field, and Enter
presses a button. A press on a control does the same as entering it: its cell becomes the active one
and the control keeps the focus, in widget mode, so <Kbd keys="esc" /> or <Kbd keys="f2" /> returns
to the cell.

The content of a detail is the same: the cell of the detail row is a place of the grid, and its
controls are reached by <Kbd keys="enter" /> or <Kbd keys="f2" /> (see Master-detail).

A title is a cell too, and <Kbd keys="enter" /> on it sorts, so its buttons are reached with the key

<Kbd keys="f2" />: the sort button first, and then <Kbd keys="tab" /> to the funnel of the header
filter (when there is one) and to the button of the column menu.

The grid leaves alone a key that something already cancelled (`defaultPrevented`), a key that an
input method owns while text is composed, a key from inside a popup that a cell holds (a `[popover]`
or a `dialog`: the list of a Select, a calendar), and a key from a grid that is itself in a cell. A
control whose popup is open (`aria-expanded="true"`) keeps <Kbd keys="esc" />, which closes the
popup; the next one is the grid's. A press in a popup does not make its cell the active one. A popup
that a cell opens in a portal, elsewhere in the page, is not in the grid at all: the focus in it
stays there when the grid draws again, since the grid gives the focus back to its active cell only
when it was in the table.

### `onRowActivate` and the focus

`onRowActivate(row, key)` is called by <Kbd keys="enter" /> on a cell that holds no control, and by
a double press on a cell, but not on a control in it, for opening the page of the row, say. It is
not called from a title. Without it neither key nor press is handled. With it, the second click of
a double press on a row does not choose, so `selectOnRowClick` chooses the row once and does not
take it off again; without it, a quick second press is a press of its own.

`ref.current.focus()` (see Handle) moves the focus to the active cell and scrolls it into view. A
key that moves the focus does so without the browser scrolling, then scrolls the cell into view by
the least it takes, which the scroll margin of the rows (the measured height of the sticky heading)
keeps clear of the heading: a focused cell is never under it. A title sticks, so it is always in
view up and down: the focus on a title scrolls the frame only sideways, and the rows stay where
they are, also when Tab comes back to the title from outside the grid. When the page has scrolled
past the heading, a key or `focus()` that goes to a title brings it back into the window.

The scroll frame has `tabindex="-1"`: Firefox puts a scrolling element in the Tab order unless it
has a `tabindex`, and the cell is the stop.

server and the first render in the browser say the same. Pass the person's language. Anything that
is not a `variant`, a `density` or a `captionAs` is the default.

`className`, `style`, `id`, `hidden`, `dir`, `lang`, `data-*` and the event handlers go to the root
element, which is a `div`; a `style` of yours is kept, with the grid's custom property and `height`
added. `data-variant` and `data-density` are the grid's own, which its stylesheet reads: yours do
not replace them. `aria-label`, `aria-labelledby` and `aria-describedby` go to the `<table>`. There
is no `children`, and no `dangerouslySetInnerHTML`: the grid draws everything inside.

`DataGridProps` is an object type, so an interface can extend it:
`interface OrdersGridProps extends DataGridProps<Order> {}`.

## Handle

The `ref` is a handle, not the element. It has eleven members:

| Member                | Is                                                                                                        |
| --------------------- | --------------------------------------------------------------------------------------------------------- |
| `element`             | The root `div` of the grid; `null` before it is mounted                                                   |
| `getState()`          | The state as the grid shows it, all eight parts: the page as drawn, the layout as shown                   |
| `focus()`             | Moves the focus to the active cell, and scrolls it into view                                              |
| `scrollToRow(key)`    | Brings the row into view, opening its groups and going to its page first; `false` when no row has the key |
| `clearFilter()`       | Clears the search and every condition, and goes to the first page                                         |
| `expandAllGroups()`   | Opens every group; nothing when they are open                                                             |
| `collapseAllGroups()` | Closes every group; nothing when they are closed                                                          |
| `addRow()`            | Adds a row and edits it, as the toolbar's button does; nothing without `editing.allowAdding`              |
| `exportCsv(options)`  | The rows as CSV text, always returned; downloads it with `download: true` or a `fileName`                 |
| `saveChanges()`       | Saves what is not saved (see Batch mode); resolves `true` when it went through, `false` when not          |
| `cancelChanges()`     | Drops what is not saved and closes any editor, the form and the popup; says nothing                       |

In `'form'` and `'popup'` mode `saveChanges()` saves the open form or Dialog as its Save does: every rule is checked, the
first field that fails takes the focus and gets its words, and a row that goes through closes it. It resolves `true` when
the row went through, when nothing is open and when the form holds no change; it resolves `false` when a rule fails, when
a save is already pending and when `onSaving` refuses.

The handle is one object for as long as the grid lives, whatever it shows. On a grid that has no row
`focus()` goes to the active title and `scrollToRow` returns `false`.

```tsx
const grid = useRef<DataGridHandle>(null);

<DataGrid ref={grid} data={orders} rowKey="id" columns={columns} caption="Orders" />;

grid.current?.scrollToRow('DH-1030');
```

| `saveChanges`, `discardChanges`                     | `Save changes`, `Discard changes`                            | The buttons of the save bar                                                                       |
| `announceErrors`                                    | `2 fields need attention`                                    | What is said when a save finds fields that fail: `(count)`                                        |
| `validation`                                        | `Customer is required`                                       | The words of a rule with no message: `required`, `range`, `stringLength`, `pattern`, `email`      |
| `moveUp`, `moveDown`, `moveToTop`, `moveToBottom`   | `Move up`, `Move down`, `Move to top`, `Move to bottom`      | The items of the row menu                                                                         |
| `reorderDisabled`                                   | `Clear sorting and grouping to reorder rows`                 | The tooltip of a handle that is off, and what the row keys say then                               |
| `announceRowMoved`                                  | `DH-1024 moved to row 3 of 12`                               | What is said after a row was moved: `(name, position, count)`                                     |
| `summaryOf`                                         | `Total of Qty`                                               | The hidden words before a total with no visible label: `(type, caption)`                          |
| `controls`                                          | `Choose date`, `Increase`, `No results`, `Clear search`…     | The words of the controls the grid draws, a record merged one level deep: see below               |

`labels.controls` holds the words of the controls the grid draws, each of which takes words of its own. Each
default is the control's own, so nothing changes until you pass them:

| `controls` key               | Default                        | Is                                                                              |
| ---------------------------- | ------------------------------ | ------------------------------------------------------------------------------- |
| `chooseDate`                 | `Choose date`                  | The name of the calendar button of a date field, and of its calendar's dialog   |
| `invalidDate`                | `Invalid date`                 | What a date field says of text that is no date                                  |
| `unavailableDate`            | `This date is not available`   | What a date field says of a date outside its `min` and `max`                    |
| `previousMonth`, `nextMonth` | `Previous month`, `Next month` | The names of the calendar's month buttons                                       |
| `increase`, `decrease`       | `Increase`, `Decrease`         | The names of the buttons of a number editor                                     |
| `noResults`                  | `No results`                   | What the list of a Combobox editor says when no choice matches                  |
| `results`                    | `1 result`, `3 results`        | What a Combobox editor announces after the text changed: `(count)`              |
| `clearSearch`                | `Clear search`                 | The name of the clear button of the toolbar's search and of the header filter's |

They reach the DatePickers of the cell editor, the filter cell and the range popover, the NumberInput and the
Combobox of the editors, and the two search fields. A record given in part keeps the words it leaves out:
`labels={{ controls: { increase: 'Tăng' } }}` changes one name.

## Do and don't

- Do give the grid a name: a `caption`, or an `aria-label`.
- Do keep `columns`, `rowClassName` and the functions of `labels` in constants, `useMemo` or
  `useCallback`.
- Do pass `locale` (and `timeZone` for a `datetime`) that the server and the browser both know.
- Do put the columns and the grid in a client component when the page is a Server Component.
- Do put a link, a button or a field of a cell in a `cell`, and not a tab stop of your own: the grid
  keeps one stop, and takes the controls of a cell out of the Tab order.
- Do give each of two grids without a caption on a page its own `labels.pagination`.
- Do pass `totalCount` with `remote`, and load the rows again in `onSortChange` and `onPageChange`.
- Do pass `selectedKeys` with `onSelectedKeysChange` when the choice is yours to keep, and keep the
  keys, not the rows.
- Do keep the rows you have while you load the next, and pass `loading`: the grid shows them under
  a layer and does not need a spinner of yours.
- Do change `data` in `onRowReorder` when you use `rowReorder`, and keep the order: the grid moves
  nothing, and the keys of the rows are what it follows.
- Do pass `csvExport` and not a button of your own, or call `exportCsv()` from yours: both write the
  same text. Export the whole data on the server in server mode.
- Do give a track or a flex item that holds a grid `minmax(0, 1fr)` or `min-width: 0`. An `auto`
  track, or a flex item, is as wide as its content at least, so a grid in one is never narrower than
  its columns and its frame never scrolls: the page does.

  ```tsx
  <div style={{ display: 'grid', gridTemplateColumns: 'minmax(0, 1fr)' }}>
    <DataGrid data={orders} rowKey="id" columns={columns} caption="Orders" />
  </div>
  ```

- Don't give two rows the same key.
- Don't expect the handles to work while the grid sorts or groups: they are off then, and say why.
- Don't sort or page `data` yourself without `remote`: the grid does, and sorting twice is wasted.
- Don't turn `escapeFormulas` off for a file that a spreadsheet will open: a name that starts with
  `=` becomes a formula there.
- Don't write a `datetime` without an offset, or a `date` that is not `YYYY-MM-DD`.
- Don't count on a text being fully visible in a cell: a long one is cut. Give the column room, or
  show the whole text in a `cell`.
