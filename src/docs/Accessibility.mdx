# Accessibility

Keyboard support, focus handling, semantics and screen-reader behaviour target WCAG 2.2 AA.

## Colour contrast: known gaps

The default theme reproduces the approved visual design exactly. In the places below that design
falls short of the WCAG AA contrast minimums. Values are the lowest ratio measured over the
reference backdrops, rounded down, and CI fails if any of them gets worse.

## Toasts

- Toasts are read from a polite live region; an error is read at once, from an assertive one. Both
  regions are in the page before the first toast, so the first one is read too.
- F8 moves focus to the toasts (the key is the Toaster's `hotkey`), and Esc closes the toast that
  holds focus. The region is a landmark named "Notifications (F8)".
- The time of every toast stands still while the pointer is over the toasts, while focus is in them
  and while the page is hidden, so there is time to read and reach a button.
- A toast must not be the only way to do or learn something: it goes away.

## Advanced inputs

- **Slider:** with `getValueText` the thumb's `aria-valuetext` is that text ("60%"), so a screen
  reader reads it where it would read "60". The bubble above the thumb repeats it and is
  `aria-hidden`.
- **Combobox:** its own live region says how many options are left ("5 results", "1 result", "No
  results") shortly after typing stops, and "Loading…" while results are fetched. `labels.results`
  changes the wording.
- **Calendar:** every day is named with its full date in the locale ("Saturday, November 14, 2026")
  and the weekday row reads the long names ("Sunday"). The month title is a polite live region.
- **Live regions:** Combobox (results), TagInput (tags added, removed or turned down, with the
  reason), FileUpload (files added or rejected) and DatePicker (an invalid date, or a date that
  cannot be chosen) each carry their own visually hidden `aria-live="polite"` region in their root,
  present from the first render. One shared region would go silent inside an open Dialog, whose
  surroundings are inert. Changes your code makes to `value` are not announced.

The contrast gaps of the Slider (rows 15 to 17), Calendar (row 18), FileUpload (rows 19 to 22),
Alert (rows 23 to 26), Progress (rows 27 to 29), Stepper (rows 30 and 31, and its part in rows 26,
27 and 29), List (its part in rows 31 and 32) and Table (rows 32 to 34, and its part in rows 2, 6,
9, 12 and 22) are in the table above, which is built from the same data CI checks.

A List row that can be pressed has one link or button, the title, stretched over the whole row. It
is named by the title alone: the description and the end cell are read when the person browses the
content, and are not part of the name, so put what matters in `title`. With `prefers-contrast: more`
the current row is the solid accent and everything in it takes that accent's text colour; a Badge or
button you put in a current row keeps its own colours, so keep that row to text and icons.

A Stepper step reads as one phrase, "Step 2 of 4: Delivery, Home delivery, Completed", from text
that is hidden from sight; the dot, the bar and the line "Step 2" are hidden from screen readers. In
the narrow form (under 480px) the words of every step but the current and a failed one are hidden
from sight the same way and are still read, so the steps do not lose their names for a screen
reader.

A Table has no live region and no cell-by-cell keyboard navigation: Tab goes through the sort
buttons and the controls in the cells, as in any table. The column that is sorted carries
`aria-sort`, and only that one does, as in the sortable table pattern; the arrow is hidden from
screen readers and the sort button is named by its title. When a table is wider or taller than its
frame, the frame becomes a named region that takes the keyboard, so the arrow keys scroll it: name
it with a `TableCaption`, an `aria-label` or an `aria-labelledby`. With
`prefers-contrast: more` the row under the pointer and the stripes of `striped` are not drawn, and
a chosen row has a 2px frame instead of a wash, so every Badge and every muted text in a row sits
on the surface.

## Alert, Skeleton and progress

None of the phase 4 components makes a live region of its own. Each says what it is, and you choose
when a change is announced.

- **Alert has no `role` by default.** Text that is in the page from the start is not read as news
  even when it has a role, and an error that a server rendered is not news, so the library does not
  make `error` an `alert`. After something the person did, choose one of two recipes. For a polite
  message, keep an empty `<div role="status">` in the page from the first render and render the
  Alert into it: a screen reader reads only what changes in a live region it already knows. For an
  urgent one, give the Alert `role="alert"` and put it into the tree after the action. Send focus
  somewhere sensible when an Alert is closed.
- **Skeleton is always `aria-hidden`.** Many blocks would be many announcements, so the container
  says "loading" once: it stays mounted, carries `aria-busy` while the work runs and `false` after,
  and a `role="status"` region that was in the page before the work started says what is loading.
  "Loading states" in Getting started shows it. A Suspense `fallback` is inserted already filled, so
  what it says is read on a best-effort basis.
- **Progress** puts its name, value and state (`aria-valuetext` carries the state too) on the
  `role="progressbar"` element. It is read when the person reaches it; the library does not announce
  each percent.

## A `<dialog>` the library did not create

The library tracks the Dialogs and Drawers it opens. A modal `<dialog>` from anywhere else is not in
that stack: the toasts, which sit in the page, become inert under it, so a keyboard or screen-reader
user cannot reach them and a pointer cannot click them. Open modals through the library's Dialog and
Drawer, or keep toasts for moments when no other modal is open.

## Other preferences

- Without `backdrop-filter` support, or with `prefers-reduced-transparency: reduce`, surfaces become
  almost opaque.
- In `forced-colors: active` (Windows High Contrast) the library uses system colours and keeps
  borders and focus outlines visible.
- With `prefers-reduced-motion: reduce` transitions stop, and so do the repeating animations of
  Progress and Skeleton: the indeterminate Progress is a still striped bar, and a Skeleton does not
  pulse, shimmer or breathe. A repeating animation cannot be stopped by a zero duration, so the
  library has a rule of its own for them. Spinners keep turning, more slowly, because a still one
  would no longer say "busy".
